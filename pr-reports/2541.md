# Lock subscription balances before a top-up or charge changes them

[Backend PR #2541](https://github.com/6529-Collections/6529seize-backend/pull/2541)

## Summary

The legacy subscription top-up and the airdrop charge each read a balance with a plain read, worked out the new total and saved it. A top-up and a charge on one key at the same time lost one of the two. A merge of consolidated wallets that committed between a writer's read and its save was overwritten, or the save updated a row the merge had deleted and the money was lost. Both writers now lock the balance before they read it, and follow a key a merge has moved. This PR is built on the key-width guard (#2524, merged) and its locking-read follow-up, and on the airdrop-once PR (#2532); the follow-up and #2532 merge first. It ships with the merge-lock PR.

## Backend impact

- `persistTopUps` and `processSubscription` read the balance `FOR UPDATE` and write it back with an explicit `UPDATE` or `INSERT`. The charge also locks its final allocation, and records the redemption under the key that paid.
- When a key has no balance row, its wallets are looked up again in `address_consolidation_keys`. If they all belong to one other key now, that key's balance is used.
- The key-width guard judges the key the write lands on, after the lock, and queues the write under it.
- MySQL tests run the real top-up and charge code against each other and against a merge. All seven fail on the code before this PR. Two more check the guard on a moved key. All suites pass on the guard with all three PRs.
- A read-only query in the PR lists balances left under a key a merge folded away. The merge-lock PR's balance check covers lost top-ups and charges.
- The processing loop now holds its locks for its whole run, so a deadlock with a merge is slightly likelier. MySQL rolls one side back, and that loop retries on its next run.

## Backend deployment

After the key-width guard (#2524), deploy `transactionsProcessingLoop` and `subscriptionsTopUpLoop`, with the merge-lock PR's `delegationsLoop`. There is no migration, flag or configuration. To roll back, revert the three commits.
