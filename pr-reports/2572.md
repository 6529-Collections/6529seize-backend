# Signed records take anchors and owners from the chain gateway

[Backend PR #2572](https://github.com/6529-Collections/6529seize-backend/pull/2572) · stacked on [#2515](https://github.com/6529-Collections/6529seize-backend/pull/2515)

## Summary

Signed records need two things from the 6529 chain: the height a record is anchored at, and which principal each wallet is bound to. The code to read them is merged (`wireSignedRecordsChain`, #2526), and #2515 adds the client that reads the chain gateway. Nothing called the one with the other, so `GET /signed-records/anchor` and `/owners` answer 503, and the record submits in #2546 would refuse every record.

This PR makes the call at startup, in two places:
- **the API**, after its secrets load;
- **`signedRecordLogLoop`**, once the record log is on, for the tasks that read records (the personal import in #2546). Closing and archiving segments read neither anchors nor owners.

**When the gateway is configured** (`CHAIN_GATEWAY_URL`, as #2515's client accepts it), signed records take anchors and wallet owners from the shared client.

**When it isn't,** nothing is wired. One warning line says why, without the setting's value, and the anchor and owners routes answer 503 `ANCHOR_UNAVAILABLE` and `OWNERS_UNAVAILABLE`, as they do today. The line is logged once per process while the outcome stays the same.

**The anchor never goes back on a network.** It is the highest finalized height, with its block time, served so far on the head's network, kept per network as the client keeps its pin floors.
- When the client pins above a lagging node's finalized height, the head has no block time for the pin, and the node's own height can be lower. The anchor stays at the height already served, so a record signed at it a moment ago is still near the head.
- A first head with no block time at all on its network answers 503 `ANCHOR_UNAVAILABLE`, saying so.
- A new network (a relaunch) starts from its own heights. A node that answers for another network and back leaves each network's height where it was.

**Read failures:** when the anchor or owners read fails, the cause (its code and message) is logged once at warn, until a read succeeds again.

## Backend impact

- **With `CHAIN_GATEWAY_URL` set:** `GET /signed-records/anchor` and `GET /signed-records/owners` answer from the chain instead of 503.
- **Without it:** nothing changes.
- This PR writes nothing. No new routes, tables, flags or settings; `CHAIN_GATEWAY_URL` and `CHAIN_GATEWAY_SERVICE_KEY` are #2515's.
- **Why no switch of its own:** every write that depends on the wiring sits behind #2546's `PERSONAL_RECORDS_MODE`, which defaults to `legacy`.

## Deployment

**Stacked on #2515:** merge #2515 first.

**Order:**
1. #2515 deployed, with `CHAIN_GATEWAY_URL` (and `CHAIN_GATEWAY_SERVICE_KEY`) set on the API and on `signedRecordLogLoop`.
2. This PR: `api`, then `signedRecordLogLoop`.
3. Only then any signed records mode: personal settings' `PERSONAL_RECORDS_MODE=shadow`, then `primary` (#2546). Unwired, every record there is refused, in shadow too.

**Smoke checks:**
- The API's start-up log has `[WIRED]` from `SIGNED_RECORDS_CHAIN`, not `[NOT WIRED]`.
- `GET /signed-records/anchor` answers an anchor, head height and finalized time.
- `GET /signed-records/owners?wallets=<a wallet>` answers its owner.

## Rollback

1. If `PERSONAL_RECORDS_MODE` is `shadow` or `primary`, set it back first: to `legacy`, or from `primary` to `shadow`.
2. Then redeploy the previous `api` and `signedRecordLogLoop`.

This PR writes nothing, so nothing is lost. Never roll back by unsetting `CHAIN_GATEWAY_URL`: #2515's identity reads use it.

## Tests

- **Unit:** the 7 suites around it pass (326 tests): the wiring, the anchor service, the owner directory, the signed records routes, the log loop, the API's initializer and the gateway client. They cover:
  - configured: anchors and owners come from the client, including one run through the real client's status read with a fake fetch;
  - unconfigured, four ways (no URL, a URL that isn't http(s), credentials in the URL, a service key that isn't plain visible ASCII): left unwired, even after an earlier wiring, with the anchor and owners answers as 503 and their messages, and one warning line that holds none of the setting's value;
  - the line logged once while the outcome stays the same;
  - the anchor never going back on a network: a lagging node, then a head with no block time, keep the height served; a node answering for another network and back keeps each network's height (1000, 5, 1000); a relaunch starts from its own heights; a first head with no block time is a 503 that says so;
  - a failed read's cause logged once until a read succeeds;
  - the loop wiring only after its feature check, and before its task.
- `tsc`, ESLint and Prettier are clean.

## Known limits

- **The rebuild check** doesn't take the gateway yet. In a run, the personal settings step (#2546) reads every wallet as unbound, so a record in a principal's stream fails verification and the step stops on it.
