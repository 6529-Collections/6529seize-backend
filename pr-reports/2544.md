# Profile sites on the 6529 chain (backend)

[Backend PR #2544](https://github.com/6529-Collections/6529seize-backend/pull/2544) · builds on the signed records PRs #2523 and #2526 (merged)

## Summary

A profile site's primary pointer moves from MySQL to the person's ProfileDoc on the 6529 chain. Two keys name the site by CID, `cms.primary.publication` and `cms.primary.package`, and the person moves them with PROFILE_REPLACE. 6529.io's profile CMS tables become an index of the chain, rebuilt from it. A third key, `cms.archive`, carries each person's 6529.io site history in at the identity import.

The PR also adds the export the identity import needs at the freeze, retires legacy CMS writes, and logs drafts and BYO agent records to the interim record log so they can be rebuilt.

The export runs as a job of `dbDumpsDaily`, invoked by hand at the freeze: it reads the read replica in one read-only snapshot, writes the export's files to a private bucket, and returns download links. The identity export finds it there by the freeze.

Nothing changes while `FEATURE_PROFILE_CMS_CHAIN_POINTER` and `FEATURE_PROFILE_CMS_PERSONAL_LOG` are off, their defaults, except at the identity freeze: from the time in `IDENTITY_FREEZE_AT` (or with `FEATURE_IDENTITY_FROZEN=true`), publish, rollback, unpublish, archive and the legacy CMS writes answer 423 `IDENTITY_FROZEN` while the chain flag is off. The daily dump runs as before; the job runs only when invoked.

It targets `main`.

## Backend impact

- **New tables** (additive): `profile_cms_chain_heads`, the index's cursor per principal, and `profile_cms_chain_parked`, its retry list of changes that wait.
- **New nullable columns:** `publication_cid` on packages; `chain_height`, `doc_cid` on pointer events. No new index: the one on `publication_cid` comes later (below).
- **API, only with a flag on:** publish stores the signed publication and returns the draft with `publication_cid` (502 `cms_doc_store_mismatch` if the document store disagrees); unpublish answers 409 `cms_pointer_on_chain`; rollback answers 409 only after checking the target as the chain index and public reads will (409 `cms_profile_changed` for a former handle, 422 `cms_rollback_target_refused`, or 503 `cms_check_unavailable` when it can't check now); legacy CMS writes answer 410 `cms_legacy_retired`.
- **API, at the identity freeze, with the chain flag off:** the profile site and legacy CMS writes above answer 423 `IDENTITY_FROZEN`, as the identity routes do. With the chain flag on, the chain flag wins.
- **No new loop:** the follower runs at the end of each identity mirror run, once the follow-up wires it in (below). A change that waits is parked and retried every pass while everyone else's are applied; one parked for more than 30 minutes logs the operational error `PROFILE_SITE_CHANGE_STALLED`, once; the monitoring contract names it.
- **The export job in `dbDumpsDaily`:** an event naming `profileSiteExport` runs the export; `profileSiteExportLinks` renews a run's links. The schedule's event and an empty one still run the daily dump; any other event fails, so a misspelt job never runs the dump. The job reads only the read replica (`DB_HOST_READ`, a read-only server), in one consistent read-only snapshot taken 2 to 90 minutes after the freeze, and reads `IDENTITY_FREEZE_AT` from the `prod/lambdas` secret at each run. It writes `files/<cid>`, `cms-fields.json`, `report.json`, `links.json` and a manifest under `profile-site-export/<stage>/` in the private bucket `6529-chain-exports-<account>-<region>`, plus a pointer at `profile-site-export/<stage>/by-freeze/<frozenAt>.json`, and returns presigned links valid for at most 6 hours. A rehearsal (`"rehearsal":true`) writes the same files under a `-rehearsal` prefix with a manifest the import never takes. The runbook is `ops/chain-exports/README.md`.
- **Commands:** `profile-cms:export` (the same export from a checkout, the job's fallback), `profile-cms:chain-sync` (the side-by-side check), `profile-cms:log-existing-rows` (when the private log goes on). The CLI and the job write the same `cms-fields.json`.

## Backend deployment

1. With #2523 and #2526 deployed: `dbMigrationsLoop` (full scope), then `api` and `dbDumpsDaily`, flags off. The schema change is two new tables and three nullable columns.
2. Before the freeze, once: the bucket stack in each region (`ops/chain-exports/chain-exports-bucket.yaml`, administrative credentials) and `IDENTITY_FREEZE_AT` in the `prod/lambdas` secret. Then a rehearsal on staging and the production timing run, as the runbook says.
3. At the identity freeze (T, planned Tue 24 Nov 00:00 UTC): invoke the job from 00:05 UTC, and before 01:30. The identity export reads its pointer for the freeze.
4. After identity switch-on (planned Wed 25 Nov 00:00 UTC), once the follow-up that wires profile sites to the identity mirror is merged and deployed: the side-by-side check (it needs the follow-up). When it passes and the frontend PR is deployed: `FEATURE_PROFILE_CMS_CHAIN_POINTER=true` for `api` and the identity mirror loop.
5. With the personal records switch: `FEATURE_PROFILE_CMS_PERSONAL_LOG=true` for `api` first, then `6529 run profile-cms:log-existing-rows` once, with the same flag set.

**Rollback:** set either flag to `false`. The old code reads and writes the same tables; nothing on the chain needs undoing. The tables and columns are additive. For the job: redeploy `dbDumpsDaily` from the previous ref; the bucket and its files stay until they expire after 30 days.

## Rebuild

- **From the chain:** `rebuildProfileCmsFromChain` replays the Profile changes and the files the documents name. A change still unreadable after its tries fails the rebuild. It refuses until the follow-up is merged.
- **With the private log:** `rebuildProfileCmsFromChainAndLog` adds drafts, 6529.io's own pointer events and publish signatures, and agent records, each right after the chain change it was stamped with. It waits for the records wave reader.
- **Known limit:** a rebuild step that names its gateway is checked against the `CHAIN_GATEWAY_URL` environment variable only; if the URL is set only in the shared secret, set the variable too.
- **Known limit:** Pointer moves made on the old path while the chain flag is rolled back are not on the chain. With the private log on they are logged, supersedes included, so a rebuild from the chain and the log gives the same rows; with it off they live only in MySQL. Either way the person's ProfileDoc still names the earlier site: before rolling forward, list those moves and have those people repeat them on the chain.

## Risks and follow-ups

- **The job's database login:** it connects to the reader with `DB_HOST_READ`, `DB_USER_READ` and `DB_PASS_READ`, not the IAM database login. Those settings stay in `prod/lambdas` through the freeze; without them every run refuses, and the export falls back to the command.
- **A failed run at concurrency above 1** closes its snapshot while its other workers may still be finishing. Its prefix has no manifest, so it is never taken as the export; waiting for every worker before closing is a follow-up.

- Archiving no longer hides a package from the chain: every package that was ever primary stays in the person's history file. Public reads still serve only the primary.
- Drafts in the private log are signed by 6529.io's service key; a device-signed record per draft comes later.
- **Tests:** unit tests pass, the export job's included (the handler, the dispatch, the replica snapshot, the private bucket, the fresh secret read, the export run); the DB tests, the job's two among them, ran against a local MySQL 8.0, and CI runs them on Testcontainers. A test of the identity mirror's decoder runs once that code is on the same branch (`PROFILE_CMS_REQUIRE_IDENTITY_DECODER=true` in CI makes it required).
