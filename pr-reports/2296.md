# PR Report: Sender-independent NFT history

PR: https://github.com/6529-Collections/6529seize-backend/pull/2296
Branch: `agent-prxt/nft-history-any-sender` → `main`
Related PRs: predecessor fixes [#2259](https://github.com/6529-Collections/6529seize-backend/pull/2259) and [#2260](https://github.com/6529-Collections/6529seize-backend/pull/2260).

## Summary

Remove the remaining deployer-wallet restriction from NFT history discovery. Alternate-wallet initializations and first public or airdrop mints now share the ordered metadata history planner. The collection-wide screen identified missing Mint histories for Memes #557/#569 and MemeLab #57/#60/#61; bounded manual source replay can propose their verified claim mappings and first Mint baselines.

## What Changed

- Discover creator mint/URI logs and verified claim-extension initialization/update events regardless of sender. Paginated calls to creator contracts cover eventless top-level URI setters.
- Verify claim/token association from historical state and receipts; claim IDs need not equal token IDs. Mint recovery proves first positive supply and transaction-position URI. Existing baselines are preserved, including their dates.
- Add `nft-history-source-replay` with version-2 manifests, read-only chronological dry-run, immutable approvals and resumable atomic mapping/history/cursor writes. Original update-only jobs retain their version-1 mode.
- Support historical mapping verification on older claim generations and avoid refetching unchanged successor metadata for settings-only events.
- Preserve chronological edits, repeated-URI identity, fail-closed checkpoints and the normal scheduled ingestion checkpoint during replay.
- Enforce the invocation time budget inside creator-call pagination and transaction discovery. Normal ingestion discovers 20-block chunks, checkpoints only complete blocks and resumes at checkpoint + 1. Completed prefixes survive later failures; partial blocks are replayed without skipping their remaining sources. The URI decoder independently restricts its creator contracts.
- Ignore unlisted claim-signature logs incidental to a legitimate mint receipt; explicit audit discovery still reports those unknown emitters.

## Backend Impact

- Changed service and sole required deployment: `nftHistoryLoop`.
- No new service, schema synchronization, entity/migration, API/frontend contract, schedule or queue.
- Reuse the existing history event/job tables and API reader from the predecessor rollout. Archive-capable Ethereum RPC and creator-scoped Alchemy discovery remain required.
- Recovery uses the application planner; no manual SQL or full history reset is required.

## Config / Env

The existing Lambda environment flag `NFT_HISTORY_REPLAY_APPLY_ENABLED` remains disabled unless exactly `true`. Manual apply/resume requires separate execution approval and this explicit gate; restore it to `false` after completion or failure. Normal ingestion and dry-run do not require apply enabled. No new environment flag is introduced.

## Risks / Follow-Ups

- Deployment alone cannot repair initialization/Mint records behind the existing checkpoint. Recover verified historical mappings and Mint baselines through source replay before expecting blocked pending updates to resume.
- Stage the new ingestion and recovery paths before production. Review fresh manifests for all five missing baselines, including adjacent source transactions and failures; retain coverage receipts between bounded windows. #57's initialization and first paid mint require separate windows because they are more than 2,000 blocks apart.
- Unsupported layouts, unknown mint sources, missing first-supply evidence and unprocessable metadata stop the current window. Monitor checkpoint age and resolve the named transaction before resuming.
- Normal catch-up is capped at 1,000 blocks per invocation. Monitor lag after outages; the runbook gives checkpoint-age thresholds and approximate backlog-drain capacity.
- Forwarded metadata operations need exact execution calldata. Eventless forwarded URI setters additionally need execution-trace discovery and are outside this direct-call scanner's coverage.
- Real MySQL transaction/JSON behavior and deployed API/Timeline reconciliation still require integration/staging validation before rollout.
- #275/#304 legacy attribution corrections remain separate reviewed repairs; this source mode does not silently erase legacy no-op rows or move their records.
