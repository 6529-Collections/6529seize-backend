# PR Report: Meme collaborator invitations

PR: https://github.com/6529-Collections/6529seize-backend/pull/2162
Branch: `agent-prxt/meme-collaborator-invitations` → `main`
Related PR: https://github.com/6529-Collections/6529seize-frontend/pull/4243

## Summary

Artwork submitters can invite multiple collaborating profiles. Each invitee accepts or declines directly; acceptance is final. Voting continues while invitations are pending. Public attribution and collaborator profile submissions/wins include accepted collaborators only.

## What Changed

- Store artwork/terms snapshots and independent invitation statuses. Pending identities are private to the submitter and their own invitee; proxy consent is forbidden.
- Use a shared transaction lock for acceptance and legacy/designated native Main Stage mint selection. Selection freezes the accepted roster and closes unanswered invitations.
- Build initial Artist and SEIZE Artist Profile traits as comma-separated lists from the saved accepted roster, with Collab derived from that roster. Admins can edit all final claim artwork and traits in Craft. Arweave publishes the saved claim without invitation or collaboration-snapshot checks.
- Add invitation/acceptance notifications through existing notification and push pipelines. Ownership, voting budgets, submission allowances and configured airdrops retain their existing behavior.
- Preserve the original artist name when edits round-trip the API’s combined credits, and keep that original-name field redacted for moderated artwork.
- Existing submissions/claims without managed records stay compatible. New submissions, including resubmissions, obtain fresh invitations.

## Backend Impact

Two synchronized entities (`meme_collaborations`, `meme_collaboration_invitations`) and generated collaboration state/response endpoints are added. Drop V1/V2 attribution and Main Stage profile queries expose accepted collaborators. No new Lambda, queue, event transport, on-chain contract, environment variable or configuration is introduced. Architecture documentation is updated; the companion frontend updates the help corpus and generated contract.

## Release Notes

Acceptance is final and prevents the submitter from replacing the accepted artwork or original artist name. Admins retain final authority over mint artwork and credits in Craft, including manually crediting an unaccepted artist. Manual mint credits do not accept invitations or change accepted-submission profile attribution. Pending invitations never delay minting. Collaborator credit grants neither editing rights nor payment splits.

## Risks / Follow-Ups

Consent pins stored submission fields and media URLs; externally hosted dynamic content retains its existing mutability.

Retain consent records and snapshot-aware workers while managed claims remain in flight if reverting the feature. Never drop the new tables as part of rollback.

Consent copy clarifies admin authority over final mint artwork and credits, with acceptance copy version 2. Consent terms are pinned when the invitation is created. Editing an unaccepted artwork changes its consent hash and requires invitees to reload/review; later wave-term edits do not rewrite that invitation's terms. Roster ordering uses persisted creation time and UUID, so ties remain stable without implying artist seniority.

Public collaborator links use current profile handles; initial claim attributes use the selected handle strings, subject to admin edits. Collaboration lookup is batched per drop page (including replies and quotes), with the accepted result reused for presentation. Collaboration pushes use the existing mention preference; the in-app invitation remains available when pushes are muted. Artist profile attributes intentionally follow the existing comma-separated metadata contract.

Invitation-state reads use the primary database. Viewer-specific endpoints prohibit shared caching, and committed responses survive websocket delivery failure. Reply and quote copies receive managed credits before moderation redaction. Invitation profile lists are create-only; artwork edits cannot replace them. Push routing resolves the artwork serial number used by the existing Waves redirect.

Invitation and notification inserts intentionally execute sequentially on the same MySQL transaction connection. The bounded roster has at most 20 invitees; parallelizing these dependent writes would not provide independent transaction work. The two await-in-loop maintainability suggestions are deferred for that reason.
