# Signed records: device-signed records and an interim record log

[Backend PR #2523](https://github.com/6529-Collections/6529seize-backend/pull/2523) · [Frontend PR #4994](https://github.com/6529-Collections/6529seize-frontend/pull/4994)

## Summary

A backend module for signed records: public or private records a person's device signs with its existing device key, under the device grant it already holds. They use the "6529 Network P2P" device-signed event of signed drops, under the `post` scope, so there is no new wallet prompt. Private records are sealed with a per-device sender key, which is wrapped to 6529.io's provider keys (HPKE, RFC 9180). The module verifies records, opens the ones 6529.io may read, and indexes the newest change per key through handlers that later features register.

An interim record log keeps accepted records until the 6529 network relays carry each person's streams. Every five minutes, hash-chained segment files go to IPFS, with each segment's head posted as a signed drop in a public records wave. Every hour, the segments go to Arweave and are listed in an archive drop.

Nothing calls the module yet, and the log's loop does nothing while `FEATURE_SIGNED_RECORD_LOG` is off.

## Backend impact

- **New tables** (additive, entity sync): `signed_record_heads`, `signed_record_log_entries`, `signed_record_log_segments`.
- **New loop** `signedRecordLogLoop`:
  - `signedRecordLogCloser` runs every 5 minutes;
  - `signedRecordLogArchiver` runs hourly at :07;
  - each has reserved concurrency 1.
- **New endpoint** `GET /signed-records/anchor`: the finalized height to sign as a record's anchor. It answers 503 until the chain gateway client is wired in.
- **CORS:** `x-6529-signed-records` is an allowed request header.
- **Logs:** queries on private table families, signed records included, are logged as `[private <family> query]`.

## Backend deployment

1. `dbMigrationsLoop` (full scope).
2. `api`.
3. `signedRecordLogLoop`, after its permissions, the service identity, the provider keys and the records wave exist.
4. Set `FEATURE_SIGNED_RECORD_LOG=true` when a feature that writes records ships.

**Rollback:** `FEATURE_SIGNED_RECORD_LOG=false`. Queued entries wait and nothing is lost. The tables are additive; `dbMigrationsLoop` needs no rollback.

## Rebuild

- **The segment table:** the closer restores missing rows from the records wave before it opens a segment, so an emptied or older table never forks the chain while 6529.io's drops of the records wave are current. After any database restore, and during a rebuild, keep `FEATURE_SIGNED_RECORD_LOG` off until those drops match the relays.
- **From the log:** walk the head drops in the records wave, fetch the segments from IPFS or Arweave, and check the sha256 chain. Then verify each record against the grant proof it carries; contract-wallet grants are checked with EIP-1271 against Ethereum.
- **From the relays,** once they carry the streams: the same verify and merge order.
- **Known limits:**
  - The open segment (up to five minutes) is lost with the database.
  - EIP-1271 reads current contract state, so records under a contract wallet whose owners changed since signing don't rebuild. An archive-node check comes later.

## Risks and follow-ups

- **Follow-up PR:**
  - cache EIP-1271 answers per proof;
  - keep the gateway head a few seconds on the anchor endpoint;
  - test the Ethereum check's outcomes.
- **Wiring the chain gateway client** turns the anchor endpoint on.
- **Tests:** the DB tests ran against a local MySQL 8.0 with the binary log off; CI runs them on Testcontainers.
