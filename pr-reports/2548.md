## Summary

`notification_view` is notifications as a table derived from source events: the identity mirror's rating changes, the waves chain index, the drop index and signed records. What it cannot derive goes into an archive in the private record log.

For the causes whose feeds run, a rebuild from the archive and the feeds gives the same API answers, ids and read state included. One feed runs so far: ratings, from Sat 28 Nov 00:00 UTC, when they leave 6529.io.

This PR adds:

- the view, and a switch that moves each cause on its own, in windows of time;
- rules for 16 causes, the feed runner, and the ratings feed run every minute from `delegationsLoop`;
- pushes and notification frames that follow the view;
- the archive and the rebuild.

Everything is behind `NOTIFY_VIEW_MODE`, which defaults to `off`. With the flags unset, nothing changes.

## What Changed

- New tables: `notification_view`, `notification_view_cursors` and `notification_view_push_outbox`.
- `NOTIFY_DERIVED_CAUSES` takes windows: `CAUSE@startMs`, or `CAUSE@startMs..endMs` once a cause is handed back to its old writer; a later window derives it again. Old writers compare the windows with write time, the deriver with event time.
- Every source event carries its origin; imports notify nobody, and neither does a chain change with an unknown writer.
- The view keeps every derived row except rows that name deleted drops. Mutes, blocks, moderation and preferences apply when the view is read. Copies and pushes are filtered once, as today.
- In `shadow`, a cause whose window has started (ratings, from Saturday) is written by the deriver with its `identity_notifications` copy and push, so people see it at once; read marks reach the view and the log.
- In `on`:
  - readers, badges, mark-read, pushes and frames use the view;
  - deletes, edits, merges, visibility changes and the legacy DM purge keep it in step.
- The archive keeps, as `notify` entries in the private record log:
  - CARRIED rows: the switch's bulk copy through `seal`, and later rows as they are written;
  - each derived cause's windows, and read marks;
  - deletes, merges and visibility changes.
- The rebuild checks before it changes anything (the logged windows must be earlier states of the flags), then restores, replays and applies the logged changes in order. It also names each derived row's copy again.
- The ratings feed reads the mirror's table in id order, names each change by the mirror's key, and keeps a change whose rater or target has no profile yet waiting, for up to 15 minutes, while the rows after it go on. Only a rater's own change notifies.
- Switch steps live in `ops/scripts/notification-view/cli.ts`.

## Backend Impact

- New services: none. The feeds run at the end of each `delegationsLoop` run, a failed one too, so after the identity mirror: one import and two lines in the handler's existing `finally` block, which #2516, #2525 and #2527 don't touch. A loop of their own comes with the waves feeds.
- Changed services:
  - `api`;
  - `pushNotificationsHandler`;
  - `delegationsLoop`;
  - every loop that writes notifications: competition events, voting credit returns, artwork alerts, subscription coverage and priority alerts.
- API: no contract change. In `on`, ids of rows created after the switch, and of Saturday's rating rows, are time-based.
- DB/entities/migrations: three new tables from their entities, created by `dbMigrationsLoop`.
- Queues/integrations: the push queue gains `{view_notification: {identity_id, source_key}}`. The private record log receives `notify` entries.
- Cost: in `on`, an old writer's single write takes about 1 ms more on a local MySQL 8.0 (2.3-2.5 ms to 3.3-3.5 ms, E2EE messages and coverage alerts alike): the view row and a record-log entry of about 490 bytes.

## Config / Env

- `NOTIFY_VIEW_MODE`: `off` (default), `shadow` or `on`.
- `NOTIFY_DERIVED_CAUSES`: windows, `CAUSE@startMs` or `CAUSE@startMs..endMs`, comma-separated. Starts and ends are later than the deploy that sets them, and a cause's windows only grow.
- `NOTIFY_LEGACY_OUTPUT`: `true` (default) or `false`. Turn it off only after the rebuild check.
- `MAIN_STAGE_DECISION_IDS`: the chain decision ids whose submissions are Main Stage artwork alerts.
- These are read on every call. Set them the same in every service that writes or reads notifications.
- Rollback:
  - `on` → `shadow` while legacy output is on;
  - `shadow` → `off`;
  - one cause goes back to its old writer by closing its window;
  - ratings have no old writer after Sat 00:00 and roll back by fixing forward.
  - Client effects of a rollback: the desktop app's last-seen id stays above every old id until it is reset, and pushes sent in `on` carry ids the feed no longer shows.

## Risks / Follow-Ups

- Still to come:
  - every feed except `identity:ratings`, and a loop of their own;
  - the waves and drop indexes' event logs with origins, `deleted_drops` kept from tombstones with a call to the drop-notification cancellation, the visibility call, and the applied hook;
  - a follow feed;
  - a CLI step for the rebuild.
- Every service that writes notifications must run this code before any flag is set.
- Count `identity_notifications` before the bulk copy; `copy-old-rows` runs in batches of 2,000; each run reads the newest 10,000 ids again, and `--full` reads every row.
- Known limit, for the waves-feed follow-up: when two identities merge and both hold the same derived row, the source's row goes but its `identity_notifications` copy stays, now under the target, and a later `copy-old-rows` (always `--full`) carries it, so the target sees that notification twice, as the old table already shows it. A rating notifies one person, so ratings cannot produce this; before a cause whose event reaches more than one person joins, the follow-up deletes such a copy with its row.
- The frontend should reset the desktop app's last-seen id when the newest id in a page falls below it (a rollback from `on`). At `on` itself, Saturday's unread rating rows show once more as new desktop notifications, since their ids rise.
- The feeds wait for each `delegationsLoop` run; after a long run, a row derived past its push window (15 minutes after its event, 30 for ratings) is listed but not pushed.
- A rating whose rater or target stays unmapped for more than 15 minutes notifies nobody.
- Poll-ballot notifications of waves that move to the chain stop from Sun 00:00 until the follow-up PR's waves feed derives them, with a window from Sun 00:00, so the ballots in between appear then, without late pushes. Polls in members-only waves stay on 6529.io with today's notifications.
- A cause moves to the deriver by opening its window; the gate skips every old writer of it, so the old notifiers need no setting. The gate is per cause, so a waves cause may join only once it also checks that the wave has moved (the chain holds a LegacyId for it): members-only waves stay on 6529.io and keep their writers.
- `NOTIFY_LEGACY_OUTPUT=false` stops only the deriver's copies; old writers, including those of members-only waves, keep writing.
- The behaviour of read-time filters awaits product confirmation.
