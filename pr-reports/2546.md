# Personal settings as signed records: shadow, then primary, with a one-time import

[Backend PR #2546](https://github.com/6529-Collections/6529seize-backend/pull/2546)

## Summary

Twelve personal settings move onto signed records that a person's device signs:
- follows;
- mutes, blocks and hidden drops;
- bookmarks;
- artwork alerts;
- pinned waves;
- wave notification settings;
- preferences (direct messages and notifications);
- mention shortcuts;
- push settings;
- EULA consent.

A follow of a person is a public record. Every other setting, follows of waves and drops included, is sealed so only 6529.io and the person's devices can read it.

The tables stay where they are, and every read route answers as today. The one addition is that `GET /v2/waves/pinned` gives each pin's saved position. What changes is where a write comes from: in `primary` the records are the only write, and the settings tables can be rebuilt from them.

**Nothing changes until `PERSONAL_RECORDS_MODE` is set.** Unset, it is `legacy`.

The switch goes:
1. `legacy`;
2. `shadow`: today's write, plus the same change sent as records that are checked and logged, never applied;
3. a freeze, a one-time import of today's rows into the record log, and the rebuild check;
4. `primary`.

The PR also adds:
- the rebuild check's step for these tables (`personal.settings`);
- its seed (`personal.seed`), which writes the probe rows and runs the switch;
- a probe for every read route.

## Backend impact

- **New routes:**
  - `POST /signed-records`: auth, no proxies, 1 to 16 events.
  - `GET /signed-records/mode`.
- **Changed route:** `GET /v2/waves/pinned` adds `pinned_position` to each wave's profile context.
- **Today's settings routes** write as today in `legacy` and `shadow`. In `primary` they answer 409 `PERSONAL_RECORDS_REQUIRED`. While frozen, every settings write answers 503 `PERSONAL_SETTINGS_PAUSED`.
- **New table:** `personal_records_state`, which holds the freeze and the import's order key.
- **`signedRecordLogLoop`** takes three operator tasks: `personal-freeze`, `personal-import` and `personal-unfreeze`. None of them posts anything. Freeze and import refuse with "signed record log off" while `FEATURE_SIGNED_RECORD_LOG` is off, and with "no records wave set" while `SIGNED_RECORDS_WAVE_ID` is unset or `none`. Unfreeze always runs, as the way back, even with `FEATURE_SIGNED_RECORD_LOG` off. Any other task name fails with "unknown task <name>". Nothing deployed sends one: the two schedules send no task (their job comes from `SIGNED_RECORD_LOG_TASK`), the deploy workflow only reads the two functions' code digests, and the runbooks use only these three.
- **New flag:** `PERSONAL_RECORDS_MODE`, unset by default.

## Deployment

**Builds on #2542** (the rebuild check) and **#2569** (its step needs and shared tables, so personal settings can declare their part of `signed_record_heads`), both merged, as are the signed records PRs #2523 and #2526.

**Prerequisites:**
- #2523 and #2526 deployed with `FEATURE_SIGNED_RECORD_LOG=true`;
- the chain gateway client wired in (`wireSignedRecordsChain`; no PR yet; the call with #2515's client): wiring deployed, then shadow and primary. Without it there is no anchor and no wallet owners, so every record is refused live, and private records can't be verified in a rebuild;
- `SIGNED_RECORDS_PROVIDER_KEYS` and `SIGNED_RECORDS_SITE_READER` set on the API;
- on `signedRecordLogLoop`, before the freeze: `FEATURE_SIGNED_RECORD_LOG=true` and a records wave set in `SIGNED_RECORDS_WAVE_ID`. Without either, the freeze and the import refuse.

**Deploy with `PERSONAL_RECORDS_MODE` unset**, in this order:
1. `dbMigrationsLoop` (`personal_records_state`);
2. `api`;
3. the frontend built with `NEXT_PUBLIC_FEATURE_PERSONAL_RECORDS=true`;
4. `signedRecordLogLoop`.

**Smoke checks, in legacy:**
- Follow, mute, pin and preferences save as today.
- `GET /v2/waves/pinned` carries `pinned_position`.
- `GET /signed-records/mode` gives `{mode: legacy, frozen: false, owner}`.
- `POST /signed-records` answers 409 `PERSONAL_RECORDS_OFF`.

**Turn on in this order, and check after each step:**
1. `PERSONAL_RECORDS_MODE=shadow`. Expect `[PERSONAL RECORDS] mode=shadow` log lines with refusals zero or explained, and head drops in the records wave.
2. `{"task":"personal-freeze"}`. Settings writes answer 503 `PERSONAL_SETTINGS_PAUSED` within 5 s.
3. `{"task":"personal-import"}`. Check the `[PERSONAL IMPORT] N entries … skipped {…}` line, and time the import.
4. The rebuild check (#2542). Everything equals the frozen tables except `frozen` in `personal_records_state`.
5. `PERSONAL_RECORDS_MODE=primary`, then `{"task":"personal-unfreeze"}`. Legacy settings routes answer 409 `PERSONAL_RECORDS_REQUIRED`, and changes in the site log `mode=primary applied`.

## Rollback

Set `PERSONAL_RECORDS_MODE=shadow`. `GET /signed-records/mode` then says shadow, and a change goes through today's route. Before any record is applied, `legacy` works too. If settings are frozen, run `{"task":"personal-unfreeze"}`, or every settings write keeps answering 503 `PERSONAL_SETTINGS_PAUSED`.

## Known limits

- **A person's own block and hide history in a rebuild:** the audit log's rebuild has to insert the rows `personalModerationAuditRows` returns. Until it does, those audit rows aren't rebuilt.
- **Private records in the rebuild check's seed:** a private setting or a keys record needs its wallet bound to a principal, which the run can't resolve until the chain gateway is wired in. The seed's live record is a public follow, so (pv, mute) and (pv, ~keys) heads come with the wiring.
- **A hide or block set through a drop report after the import:** this needs the reports rebuild to hand its effects over (`rebuildPersonalState` takes them as `reportEffects`). Until then, the rebuild leaves them out.
