# PR Report: Rebuild check: the profile site area, rebuilt from the private record log, and from the chain once its half is in

PR: [#2558](https://github.com/6529-Collections/6529seize-backend/pull/2558)
Base: #2544's branch, with #2542's head merged in; merges after #2542 and #2544

## Summary

The rebuild check (#2542) listed the profile site area (`publish`) with no seed and no rebuilder. #2544 brought the profile site index and the private record log it rebuilds from. This PR adds what the check needs to run them: a seed that writes a small world through the profile site tables' own logged write paths, the rebuild step reading the record log, and the area's manifest entries. Nothing outside the rebuild check changes.

## What Changed

- **The rebuild step** (`src/profile-cms/personal-log/profile-cms-rebuild.ts`): `rebuildProfileCmsFromChainAndLog` walks the private chain of the interim record log, using the reader the personal settings rebuild uses. It reads the records wave from the drops the records service posted, and each segment file from the run's files source. It follows `FEATURE_PROFILE_CMS_CHAIN_POINTER`, as the live index does:
  - on, it replays the chain's Profile changes through `createProfileCmsChainPort`, plus the log;
  - off, it replays the log alone, since the live index applied no chain change.
- **The seed** (`src/rebuild/areas/publish.seed.ts`) runs with the chain flag off and the private log on. For the first probe profile:
  - it publishes a site, writing what the old publish path writes;
  - it keeps a second draft;
  - it issues an agent grant, with its event and a proposal.

  It then closes its own open record log entries into a segment in the run's seed files, posts the segment's head to the records wave and follows that drop, as drop creation does. It refuses if another area's entries are open.
- **The records fixture** (the records service's identity, profile and wave, and the `SIGNED_RECORDS_*` values) is the personal area's, copied by value. The run refuses a flag two manifests set differently. The seed writes the fixture only where it's missing, so it runs alone or after the personal seed.
- **The manifest** (`src/rebuild/manifests/publish.manifest.ts`):
  - the log flags and the records fixture, with the chain flag left off;
  - `profile_cms_chain_heads` and `profile_cms_chain_parked` are no longer planned;
  - one rebuilder for all ten profile site tables;
  - probes for every GET route that reads them;
  - two request-time fields left out of one answer, each with its reason;
  - every waiver states its reason.
- **The chain half** stays planned (`publish.chain-seed`), not waived: people's Profile changes, followed live through the gateway.

## Backend Impact

**Deploy:** none. No Lambda, route, schema, schedule, queue or alarm change; no loop, route or deploy imports these files. `rebuildProfileCmsFromChainAndLog` is called only by the rebuild check.

**Live behaviour.** Unchanged.

**Other services.** None.

## Config / Env

None in any deployed environment. For its own run, the rebuild check sets `FEATURE_PROFILE_CMS_PERSONAL_LOG`, `FEATURE_SIGNED_RECORD_LOG` and the `SIGNED_RECORDS_*` fixture values: a fake records wave, service and wallet, and a provider key derived from a public label. None of these values is used in production.

## Rollback

Revert the PR. Nothing to undo in data.

## Risks / Follow-Ups

- **The chain half.** Until the identity mirror (#2516) and the follow-up that wires profile sites to it are in the check's run, with Profile changes from a devnet recording of the gateway, the area runs with the chain flag off. The legacy CMS tables and `profile_cms_chain_heads` then have no rows, and the four legacy CMS probes prove nothing. A final run reports this.
- **Production precondition.** `FEATURE_PROFILE_CMS_CHAIN_POINTER` stays off in production until the check covers the chain half this way, and until chain publishes can upload their files through the gateway.
- **The old publish path at the database level.** The seed writes what the old publish path writes rather than calling it, since that path checks storage over the network, which the check's source guard refuses.
- **One records fixture.** Once this PR and the personal settings PR (#2546) are both on `main`, a small follow-up moves the shared fixture into one module.
