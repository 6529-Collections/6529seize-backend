# Subscriptions keyed by 6529 identity

[Backend PR #2547](https://github.com/6529-Collections/6529seize-backend/pull/2547) · [Frontend PR #5026](https://github.com/6529-Collections/6529seize-frontend/pull/5026)

## Summary

Meme subscriptions move from consolidation keys to 6529 identities: a principal on the 6529 chain, or a wallet bound to none. New `subscriptions_id_*` tables hold the same state keyed by identity, loaded from an opening file cut from the legacy tables and checked against Ethereum and the legacy tables. Until a planned switch at a real mint the legacy tables stay the truth, and with the shadow flag on every loop also writes the identity tables and compares each list, phase pull, redemption run and signed change with the legacy side. `go-live` makes the switch in one step, and only when those comparisons matched. After it, people's subscription changes come as signed records, and the legacy tables are written as the rollback copy. Every write to the identity tables is journaled to the shared record log, so the tables can be rebuilt from the opening file and the journal alone, and a verifier checks the journal's money against its inputs and Ethereum. Nothing on Ethereum changes.

## Backend impact

- New tables `subscriptions_id_*` (balances, mode, choices, final rows, uploads, logs, redemptions, top-ups, a key map, a state row, cursors and comparison reports) and `subscription_rekey_fallback_state`, created by `dbMigrationsLoop`.
- The top-up, daily and transactions loops run identity writers after their legacy work, only when the shadow flag is on and a loaded opening is not suspended, or after the switch. With every flag off nothing new runs. `delegationsLoop`, `ownersBalancesLoop` and `dropForgeLaunchHandler` run changed shared code.
- Phase pulls, from the API or Drop Forge's distribution worker, split the identity rows too. In shadow that split runs after Drop Forge's preparation commits, in its own transaction holding the card's preparation row, and never after a rollback, including a worker step rolled back to its savepoint; after the switch it is part of the preparation's transaction.
- Drop Forge's reads of the final rows and the API's Public airdrop answers read the table the switch names: the legacy table before it, the identity table after. Every reader of the legacy final table is listed below.
- The four subscription write routes take an `x-6529-signed-records` header with one signed record. Before the switch they behave as today; after it an unsigned change gets 409, and the web app signs (frontend PR #5026, behind its own flag).
- The CLI `subscriptions:opening` (`cut`, `verify`, `load`, `compare`, `go-live`, `status`, `suspend`, `rebuild`, `open-writes`, `verify-journal`) runs the opening, the switch, rollback and rebuilds.
- Ten new alert codes (`SUBSCRIPTIONS_*`), listed in the PR description.
- The optional re-key fallback (`FEATURE_SUBSCRIPTIONS_REKEY_ON_MIRROR`) keeps legacy keys in step when the identity mirror regroups wallets.

## Deployment

- Deploy with every flag off: `dbMigrationsLoop` first, then `api`, `subscriptionsDaily`, `subscriptionsTopUpLoop`, `transactionsProcessingLoop`, `memesDistributionHandler`, `dropForgeLaunchHandler`, `delegationsLoop` and `ownersBalancesLoop`. Nothing changes until a flag is set. `memesDistributionHandler`, Drop Forge's distribution worker, runs phase pulls, so it must be on this code before the shadow flag is set. `dropForgeLaunchHandler` reads the final rows the switch names, so it must be on this code before `go-live`.
- Then follow the staging plan in order: the record log's closer, an opening cut and loaded, `FEATURE_SUBSCRIPTIONS_SHADOW=true`, the web app's signing flag, and a rehearsed switch.
- The shadow flag goes in the lambdas secret, and each service must pick it up. The API reads that secret only at startup and only with `API_LOAD_SECRETS=true`: check that its startup log shows `[LOAD SECRETS ENABLED true]`, or set the flag in its own environment too. A warm lambda keeps the settings it loaded. So after setting the flag, restart the API and redeploy or restart `subscriptionsDaily`, `subscriptionsTopUpLoop`, `transactionsProcessingLoop` and `memesDistributionHandler`.
- The switch itself, `go-live --signed-writes-live`, is run by the team: Tue 1 Dec 12:00 UTC if go-live's check passes on Mon 30 Nov's minted card, otherwise 12:00 UTC the day after the next real mint.

## Rollback

- Before the switch: unset `FEATURE_SUBSCRIPTIONS_SHADOW`. The legacy tables were the truth throughout.
- After it: `subscriptions:opening -- suspend` puts every service back on the legacy tables within about 2 minutes, counting the API cache. Going forward again takes a new `go-live`, which cuts from the legacy tables.

## Tests

- MySQL: 180 tests in 9 suites (the key-width guard's two among them), covering the opening, the writers in shadow and after the switch, go-live and its gate, every rebuild case, the journal's guards, the signed write paths and the re-key fallback.
- Unit: 470 tests in 56 suites, and the 8 subscription API tests that need a database.
- Type check, lint and format checks are clean.

## Known limits

- The rebuild and the daily journal check read the journal from the records wave, and no reader for it is bound yet: until then they say so and stop. After a database restore, the runbook step (suspend, then go-live before the writers run) is the guard.
- If the database is lost before the record log's closer posts, up to 5 minutes of builds, phase pulls and choices are not in the journal. Top-ups and redemptions come back from Ethereum.
- A block of airdrops larger than one run's caps is charged in one transaction: 3,502 airdrops took 167 s in a test.
- The legacy write routes check the switch's pause before their own transactions; go-live waits 10 s after the pause to cover a write in flight.
- After the switch, a reset of a card's distribution holds the subscriptions journal counter while Drop Forge sends its queue messages, and a phase pull run by Drop Forge's worker holds it while the worker clears its caches (up to 1.5 s). Other journaled subscription writes wait for it. A reset is a rare admin action.
- The go-live gate needs one phase comparison for the minted card, not one for each of its phases. A split lost after its pull committed (the process dies first, or its failed report can't be saved) leaves no report; if it was the card's last pull, the gate doesn't see it.
- The switch state is cached for up to 60 s. For that long after a `suspend`, the readers that follow the switch can still read the identity table while the writers have gone back to the legacy one.

## Readers of the legacy final table

Every use of `subscriptions_nfts_final` (`SUBSCRIPTIONS_NFTS_FINAL_TABLE`, entity `NFTFinalSubscription`) outside tests, and why it reads the legacy table or the one the switch names. After the switch the legacy table is the rollback copy: it lacks the rows of keys too long for its columns.

Moved to the table the switch names (`subscriptionTables().final`):

- Drop Forge: readiness' Public allocations, the ranked read for distributions, the unassigned-row check and the preparation's mode.
- The API's Public airdrop answers: a wallet's distribution allocations, a minting claim's airdrops and the community mint metrics' redemptions per card.
- The API's subscription reads, already in this PR: a key's final row, a phase's airdrops, the rows a phase pull reads, and the card's subscription count.

Stays on the legacy table, because:

- It is a legacy writer the switch already routes, and after the switch it writes the rollback copy: the legacy daily build and its re-key merge (`subscriptionsDaily`), the legacy redemption loop (`transactionsProcessingLoop`), and the legacy side of phase pulls and the reset.
- It is the rollback copy's own guard: the key-width guard and its queue of held writes.
- It is the opening's cut, which reads the legacy tables by design.
- It keeps the ids aligned: the identity daily build reads the legacy table's highest id, so both tables keep one id per row.
- It defines the table: the switch's legacy table set, the entity and its registrations, and the rebuild manifest's entry.
- Subscription coverage alerts read the whole legacy model (balances, modes, choices, final rows, redemptions and top-ups) by consolidation key. Moving them means coverage keyed by identity, a change of its own; until then, after the switch an identity whose key is too long for the legacy columns gets no coverage alert.

`NFTFinalSubscription` is also the name of a generated API model, used as a response type by the subscription routes; those uses read no table.
