# PR Report: Widen consolidation key columns for 16-wallet identities

PR: [PR #2522](https://github.com/6529-Collections/6529seize-backend/pull/2522)
Branch: `claude/consolidation-key-width` → `main`

## Summary

From the identity switch-on (planned Tue 24 Nov 00:00 UTC), an identity on the 6529 chain can bind up to 16 wallets, a 687-character consolidation key. The key columns held 200 or 500 characters. This PR widens the 26 columns that hold a key, in place, before entity sync. It also lets the holdings loops defer a group whose key doesn't fit instead of failing, and counts it in a metric.

The migration is requested by the 6529 chain project on 22 Nov, as AGENTS.md ("Database schema and migrations") requires; the team's approval in review completes it.

## What Changed

- **Migration `20261122010000-widen-consolidation-keys`, run before entity sync in `dbMigrationsLoop`'s full scope:**
  - **Widths.** 23 columns go to `varchar(700)`. `subscriptions_nfts` and `subscriptions_nfts_final` go to 666 and `subscriptions_redeemed` to 567; their indexes reach 3,072 bytes there. The key source tables go last.
  - **Pre-check.** It checks every column first and alters nothing on a surprise: type, collation, nullability, default, one length byte, COMPACT or REDUNDANT row format, or an index over 3,072 bytes.
  - **Safe to repeat.** It skips missing tables and columns. db-migrate runs it again as a no-op.
- **Entities:** the 26 columns take their new lengths. `consolidation_display` stays at 500.
- **Shared helper:** `runMigrationBeforeSchemaSync`, now used by both widenings.
- **Holdings fail-soft:**
  - `deferGroupsThatDoNotFit` leaves out a group whose key is longer than a loop's narrowest table. It logs the group and counts it in `6529/Holdings ConsolidationKeyDeferredWallets`.
  - `transferReconciliationDb.requeue` moves the group's wallets to the tail of the loop's queue (delete and insert in one transaction).

## Backend Impact

**Deploy order, staging first, each in a quiet window:**
1. `dbMigrationsLoop` (full scope).
2. `nftOwnersLoop`.
3. `ownersBalancesLoop`.
4. `aggregatedActivityLoop`.

**After the deploy.** No alarm watches the deferred-wallets metric yet; the person deploying checks it in CloudWatch after each holdings loop's first run, then once a day until the follow-up alarm PR lands: namespace `6529/Holdings`, metric `ConsolidationKeyDeferredWallets`, statistic Sum, dimensions `Environment` = `staging` (eu-west-1) or `prod` (us-east-1) and `Consumer` = `owners` (nftOwnersLoop), `balances` (ownersBalancesLoop) or `activity` (aggregatedActivityLoop). The metric only exists once a wallet has been deferred, so no data points is the expected result; any data point means a key column is still too narrow (check the widths with query 1).

**Schema.** 26 in-place column widenings (metadata only, `LOCK=NONE`). Each ALTER briefly waits for a metadata lock: 3 s, three attempts.

**Other services.** No API, frontend, schedule or queue change. Other services take the entity change with their next deploy.

## Config / Env

**Before the deploy.** Add `"SCHEMA_SYNC_DESTRUCTIVE_GUARD": "block"` to the shared `prod/lambdas` secret in each environment's region: staging eu-west-1, production us-east-1. Staging first.
- **Check first.** Switch only if the last full-scope `dbMigrationsLoop` runs show no `[SCHEMA_SYNC_DESTRUCTIVE_PLAN]` log and no `SchemaSyncDestructivePlan` metric with `Outcome=reported`.
- **Why the secret.** It survives redeploys of any ref, unlike the Lambda environment.

**After the migration has run,** a full sync from a ref without this commit would plan to drop and re-add the 26 key columns. With `block`, that plan is refused instead of applied. Refs before d42be9fa1 (11 Nov 2026) ignore the guard; never deploy `dbMigrationsLoop` from them.

**If a sync is refused later.** Read the logged plan. If it is expected, apply it by invoking `dbMigrationsLoop` directly with `approved_destructive_plan_sha256` (docs/schema-sync-plan-check.md).

**Team ask.** Run the two read-only pre-check queries in the PR description on the primary (`USE <app schema>;` first).
- **Expected:** `ROW_FORMAT` Dynamic or Compressed, and every index at most 3,072 bytes after widening.
- **If anything differs,** send us the output before deploying. The migration stops with nothing altered on any column it can't widen in place.

## Rollback

- **What to roll back.** Redeploy only `nftOwnersLoop`, `ownersBalancesLoop` and `aggregatedActivityLoop` from the previous ref. The widened columns stay; `down` does nothing on purpose.
- **Never roll back `dbMigrationsLoop`.** Never redeploy it from a ref without this commit.

## Risks / Follow-Ups

- **Subscriptions are capped below 16 wallets.**
  - **The caps.** `subscriptions_nfts` and `subscriptions_nfts_final` hold 15 wallets and `subscriptions_redeemed` 13.
  - **What breaks without a guard:**
    - 14-15 wallets break redemption writes;
    - 16 wallets also break subscribing and the final-list insert.
  - **The fix.** A companion subscriptions PR adds the same defer-and-log guard to the subscription writers. Holding more needs the indexes changed, in a later PR.
- **Deferred rows.** The fail-soft can only run if a holdings table is narrower than `address_consolidation_keys`. If it does, deferred identities can lose their consolidated rows until the columns are wide:
  - a reset deletes every row first;
  - a fitting group's write deletes any shared stored key.
- **Follow-up.** A follow-up PR adds alarms on this metric, with the deploy-role enrolment of the six alarm ARNs written by the team.
- **Deadline.** This PR must be deployed by **Mon 23 Nov 10:00 UTC**, before the identity data release is cut. If it is not, identities start at 4 wallets.
- **Tests.** `transfer-reconciliation.db.test.ts` was run on a development server, where its cleanup can time out (2 of 11 tests on this branch, 4 of 11 on `main`); CI runs it.
