# PR Report: Recover blocked release-note publications

PR: https://github.com/6529-Collections/6529seize-backend/pull/2248
Branch: agent-prxt/recover-blocked-release-note-publications -> main
Related PRs: None

## Summary

An exhausted release-note delivery could leave a durable publication unfinished and consume every later run's retry budget while reporting the ordering exception as a database failure. Eligible per-run publications now retain an immutable request envelope and retry schedule independently of SQS delivery attempts.

## What Changed

- Save single-service, non-PR publication requests with valid run numbers in `release_note_recovery_jobs`; duplicate delivery cannot reset the saved envelope or completed state.
- Resume pending work through delayed messages on the existing SQS queue. There is no periodic trigger or idle polling. A pending job hands off its retry before acknowledging the current delivery; a failed handoff retains SQS ownership.
- Preserve stream order before workflow settlement as well as after publication preparation. Workflow and part-budget waits defer work without adding a processing failure. Successors park behind an unfinished predecessor and are queued in order when it completes, rather than polling the blocker.
- Keep transient failures recoverable with exponential backoff, retain permanent failures for explicit operator review, and issue a clear recovery-required alert after five processing failures. Terminal-alert delivery has its own retry path, and a later permanent failure receives a fresh operator-review alert even if a transient recovery alert was already delivered.
- Reuse the existing publication baseline, part progress and deterministic drop receipts. Recovery never marks unfinished content complete or skips a blocking publication.
- Add bounded GitHub HTTP/network retries, Retry-After handling, endpoint diagnostics and queued run-number verification. Ordering deferrals leave the transaction normally rather than raising a database-failure alert.
- Preserve PR-scoped backend service grouping and legacy notification behavior. Retain transport DLQ messages for 14 days.
- Preserve first-run bootstrap behavior: retain a missing initial baseline explicitly without blocking a later deployment from creating its first publication range.

## Backend Impact

- New services: None.
- Changed services: `releaseNotesGenerationLoop`; `dbMigrationsLoop` consumes the new entity through existing TypeORM sync.
- Required service order: `dbMigrationsLoop`, then `releaseNotesGenerationLoop`.
- API: No contract or API deployment change.
- DB/entities: Add `release_note_recovery_jobs`; existing publication and stream tables retain their schema and ordering contract. No explicit data migration.
- Queues/events: Reuse the existing source queue for delayed retries and extend DLQ retention. No new queue, EventBridge rule, or IAM policy.
- Frontend/Desktop: Existing notification contracts remain compatible; no application changes or deployment required.

## Config / Env

`RELEASE_NOTES_STAGE` is populated from the worker deployment stage. Explicit operator recovery runs only when its value is `prod`; other values disable that path.

No new secret, IAM policy or monitoring rollout is required. The existing queue policy already permits the worker to send its retry messages. SQS delays are bounded at 15 minutes; longer saved deadlines hand off another delayed message without attempting publication early.

## Release Notes

Release-note publication can resume after temporary upstream failures without exhausting later releases' retry budgets. Operators can request a retry of one saved publication through the existing Lambda using `recover_publication_id`; unknown ids fail clearly and completed jobs stay completed. The recovery runbook is `ops/release-notes/recovery.md`.

## Risks / Follow-Ups

Existing exhausted messages have no saved envelope in the new table and require inspection and exact-payload replay in order. Permanent failures intentionally remain blocking until reviewed. Automatic handoffs are bounded to ten hops per SQS chain, including successor wakeups, while Lambda recursion protection stays enabled. Transport or handoff-budget exhaustion requires explicit operator recovery; the durable envelope remains saved. Keep reserved concurrency at one. Rollback must preserve and reconcile pending recovery jobs because the older worker cannot drain the new table.
