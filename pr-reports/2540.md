# Lock the subscription balances a merge sums

[Backend PR #2540](https://github.com/6529-Collections/6529seize-backend/pull/2540)

## Summary

When wallets consolidate, the delegations loop merges their subscription balances and modes under the new key: it sums them, deletes the old rows and inserts one row with the sum. The sums were plain reads, which return the transaction's snapshot from its first plain read. A top-up or charge committed after that point was left out of the sum and lost, and a mode change was undone. The merge now reads the sums `FOR UPDATE`, so it sees the latest rows and holds them until it commits.

## Backend impact

- `mergeSubscriptionsIntoKey` reads the balance and mode sums `FOR UPDATE`. Nothing else changes, and the merge takes no lock it did not take before.
- MySQL tests commit a real top-up, a real charge and a mode change just after the merge's snapshot. Each is kept. Without the lock, each is lost.
- No query can single out past cases: the merge kept no record of the sum it read, and no balance history is kept. A read-only query in the PR lists balances that differ from their top-ups less their charges, as cases to check.
- Top-ups and charges also read a balance without a lock before saving it. The companion balance-locks PR fixes that side; the two ship together.

## Backend deployment

After the key-width guard (#2524), deploy `delegationsLoop` with the balance-locks PR. There is no migration, flag or configuration. To roll back, revert the commit.
