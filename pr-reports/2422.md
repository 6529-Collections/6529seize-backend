# Per-message reply collapse

[Backend PR #2422](https://github.com/6529-Collections/6529seize-backend/pull/2422) · [Frontend PR #4778](https://github.com/6529-Collections/6529seize-frontend/pull/4778)

## Summary

Authors can group replies to one top-level chat drop while the wave uses inline replies. The whole thread, including nested replies, moves together. Authors can restore it to the timeline.

## Backend impact

- An authenticated, author-only API sets the reply placement on a top-level chat drop. Content edits preserve the setting.
- The V2 timeline and drop-ID pagination support mixed placement using existing reply ancestry. Clients opt into filtering. Reply payloads identify individual thread roots for live updates. V2 serial-number lookups resolve the top-level thread in both collapse modes for deep links.
- The drop entity and compatibility view add the placement field. Existing drops default to inline in inline waves. Individual collapse follows the wave's unread and notification rules. The mutation reads the committed placement from the writer before sending the response and live update.

## Backend deployment

The original reply-placement rollout requires `dbMigrationsLoop` for the additive column and compatibility view, then `api` and the companion frontend. The reply-link follow-up needs only `api` and then the companion frontend in environments already running the original backend changes.
