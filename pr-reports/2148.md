# PR Report: Four-wallet consolidation and shared activation policy

Related: [BE #2151](https://github.com/6529-Collections/6529seize-backend/pull/2151), [FE #4218](https://github.com/6529-Collections/6529seize-frontend/pull/4218), [Core #243](https://github.com/6529-Collections/6529-core/pull/243)

## Summary

Full-mesh consolidations can grow to four only with renewed reciprocal consent after an environment-specific cutoff. Legacy two/three-wallet eligibility remains intact. Directional block timestamps, deterministic ordering and bounded displays support the new grouping.

Four-wallet regressions protect complete TDH/holdings aggregation and season sets that require the fourth wallet. The TDH equivalence generator now includes groups of four, and collected-statistics service coverage checks that all four normalized wallets reach the holdings query without double-counting the primary wallet.

TDH ranking now resolves complete ties by lowercase wallet address or consolidation key, independent of input order. Collection comparators handle both directions of the existing total-balance criterion, and token comparators return equality for equal numeric IDs. The backend's existing wallet inclusion rule is preserved; Core #243 adopts it to exclude empty singleton candidates while retaining funded zero-score wallets and consolidation members. Scores, boosts and Merkle leaf values are unchanged. The shared contract is documented in [TDH ranking parity](../docs/tdh-ranking.md).

Partial recalculations rebuild token rank arrays against all current rows and persist rank shifts for unaffected wallets/groups alongside the recalculated subset. Exact old-membership deletion remains scoped to the affected wallets; existing scores and links are retained. This prevents deterministic rankings from becoming stale between full calculations.

## Shared activation configuration

`CONSOLIDATION_FOUR_WALLET_ACTIVATION_AT` is the single required cutoff in each backend environment’s regional configuration. Use an ISO UTC value at whole-second precision. Production launch value is `2026-10-15T00:00:00Z`; staging can use an earlier fixed value. Missing/invalid values fail settings and grouping operations; there is no date fallback.

`GET /api/settings` exposes fixed backend limits `consolidation.max_wallets` (4) and `ungated_max_wallets` (3), alongside `four_wallet_activation_at` and a derived `four_wallet_signing_opens_at` ten minutes later. The backend, Guided Setup and native Core calculations use this contract. Both limits remain backend code constants; no new secret is introduced and arbitrary larger groups are not enabled. Regional settings load once per process, so restart affected services after updates; refresh browser sessions and recalculate TDH/reconsolidations after changing a cutoff.

## Backend Deployment

Configure each region before release. Deploy `dbMigrationsLoop` for the two nullable directional registration columns, then `delegationsLoop`, `tdhLoop`, `api`, and `helpBotReplyLoop` as required by the feature’s shared-code changes. The ranking correction specifically requires `delegationsLoop` and `tdhLoop`; recalculate after deployment to publish the corrected positions. Index registrations with timestamps before the chosen activation time. No new service or queue is introduced; the public settings response adds a required policy object.

## Runtime Configuration Prerequisite

The policy-reading runtimes are `api`, `tdhLoop` and `delegationsLoop`. Both loops load configuration through `doInDbContext` before grouping; API initialization loads its configured environment/secret before serving settings and consolidation routes. Imports that only build consolidation keys do not read the policy. The key must be verified in each runtime’s regional configuration before deployment. A missing API value fails the entire settings response; the required fail-closed behavior is preserved.

## Risks / Follow-Ups

Consolidation events intentionally read and write sequentially inside one transaction. Later events for the same pair must see earlier writes; parallel execution would change registration/revocation ordering. The maintainer accepted the two Sonar `await`-in-loop suggestions in `persistConsolidations` for this correctness requirement; sequential execution is retained.

Staging and production read the same mainnet contract. Use dedicated staging wallets. Registrations before production’s cutoff must be renewed after it to qualify there; advancing staging’s cutoff does not grant production eligibility. The supplied tests explicitly configure their own cutoff.

Frontend help-corpus guidance for deterministic rank ties remains a documentation follow-up. Backend authoring facts are included in `docs/tdh-ranking.md`; the live help bot continues to consume the frontend corpus.
