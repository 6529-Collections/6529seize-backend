# PR Report: Rebuild check: relays recorded and replayed under the relays' and areas' checks

PR: [#2559](https://github.com/6529-Collections/6529seize-backend/pull/2559)
Base: #2542's branch; merges after #2542

## Summary

The rebuild check (#2542) served the relays from a stand-in: the harness relay keeps what a run publishes and checks no signatures, so `--final` never counted it, and areas that rebuild from the relays (encrypted messages today, the drop index next) could not be proven. This PR records and replays the relays the way the check already records and replays the chain gateway. A replay counts for `--final` only when every recorded event passes the signed-event check the relays run on any event and then its area's own check. The harness relay also follows the relays' CRP v1 logs and their read rules, and a new command records a whole relay without a run. Nothing outside the rebuild check and its docs changes, apart from one `package.json` script.

## What Changed

- **Record and replay** (`src/rebuild/sources/crp-relay-record.ts`, `crp-relay.ts`):
  - `relays=record:<dir>@<relay url>` (or `@relay` for a fresh harness relay) proxies the run's CRP sessions and saves the events in the relay's order, the fields the relay sent with them, `recorded_at`, payloads, the head and the waves read. `PROVENANCE.json` is written fresh each time. No file holds the relay's address.
  - `relays=replay:<dir>` serves a recording read-only; `replay:<a>+<b>` merges one per area. A PUB that isn't a recorded event under its recorded grant (both compared as canonical JSON), a read or payload the recording lacks, a recorded event that fails a check, or a payload that doesn't hash to its name fails the run.
- **Two checks on every recorded event** (`relay-event-check.ts`, `relay-checks.ts`, `relay-check.child.ts`), run in a child process under the same source guard as the seeds and rebuilders, with no database and no endpoint:
  - the signed-event check: kind and version, the canonical body against its hash and size, the id recomputed with the backend's `computeDeviceEventId`, and the Ed25519 signature by the event's device key;
  - then the area's check, named in the manifest's new `relayChecks`, which proves offline from the grant what the backend checks beyond the signed event.
- **When a replay is final:** only when the recording has events and every one passes both checks. `PROVENANCE.json`'s `made_by` and `devnet_scenario` are labels the report shows, never a basis.
- **The harness relay follows CRP v1:** a log per wave, a family of streams sharing its family's log and rseq, `SUB` per wave after its `since` cursor with `EOSE` at each head, `HIST` with the newest page when `after` is missing, and a CHALLENGE that lives five minutes.
- **The harness relay reads as the relays do** (`relay-rules.ts`), from each area's new `relayAccess`:
  - a wave of drops is open only when an area declares it; otherwise it is members-only, read by the site reader or a declared member;
  - `ps` is public; other families need a session whose grant hasn't expired or been revoked; a `pv` stream is read by its owner, or by a wallet while the owner's newest reader record for it grants it and hasn't run out; the rest by the orderer or the site reader, and `bk` streams also by their owner;
  - a wallet has only the roles its reader entry gives it; a wave a session may not read answers `EOSE` at rseq 0, and `HIST` of it answers `ERR`.
- **The registry check** refuses a relay check whose module or export is written wrong or is a test fixture, an empty or overlapping wave prefix, a reader written wrong or without a reason, a member without a principal, and an open wave that is a family or its stream. The registry test fails on a relay check module that isn't in the tree.
- **`6529 run rebuild:relay-capture`** (`src/rebuild/relay-capture.cli.ts`, `crp-relay-capture.ts`) records a whole relay with Node and this repository only, for a devnet's operator.
- **Docs** (`docs/rebuild-check.md`): the files, the checks, the read rules, when a replay is final, and one line outside the relays: a probe marks `unordered` any list the backend reads without `ORDER BY`.

## Backend Impact

**Deploy:** none. No Lambda, route, schema, schedule, queue or alarm change; no loop, route or deploy imports these files.

**Live behaviour.** Unchanged.

**Other services.** None. The relays themselves are not touched; the harness only reads their rules.

## Config / Env

None in any deployed environment. `package.json` gains the `rebuild:relay-capture` script beside `rebuild:check`.

## Rollback

Revert the PR. Nothing to undo in data.

## Risks / Follow-Ups

- **Recordings age.** A recording is only as current as the seed that made it. When a seed's events change, a replay fails with "differs from the recording" until the recording is made again.
- **Declared access only.** The harness knows wave membership and roles only from what the areas declare. A read the relays would allow from the chain's state but no area declares is refused in the run.
- **RESYNC.** The harness relay never sends `RESYNC` (it has no replay limit); readers handle it against real relays.
