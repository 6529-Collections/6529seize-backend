# PR Report: Claims Arweave upload recovery

PR: https://github.com/6529-Collections/6529seize-backend/pull/2619
Branch: `agent-prxt/claims-arweave-upload-recovery` -> `agent-prxt/unified-arweave-recovery`
Related PR: https://github.com/6529-Collections/6529seize-backend/pull/2587

## Summary

Claim publication can resume the original signed Arweave transaction after a
network failure or interrupted invocation. The worker retains acknowledged upload
progress and performs controlled retries without changing existing external-link
or completed-media reuse decisions. Source media remains at its existing URL;
no S3 uploads or copies are introduced.

## What Changed

- Compact, ownership-fenced checkpoints hold source identity/hash, signed public
  transactions and acknowledged chunk progress. Resume verifies source bytes,
  signed data root, transaction identity/signature, signer and chunk bounds.
- Metadata bytes remain fixed across retries so an interrupted final receipt does
  not create another metadata transaction.
- Preserve the shared uploader’s caller-provided transaction tags; cancellation
  options follow the existing tags argument so subscription uploads stay compatible.
- Recoverable failures use short bounded backoff; deadline handoffs retain work
  and request prompt continuation on the existing SQS message. A crashed worker
  recovers through database-clock lease expiry.
- Application failures are counted separately from successful continuations.
  Terminal failures persist their outcome and clear publishing intent.
- Metadata identity also pins resolved meme/season values and completed media
  locations, rejecting changed mappings before reusing frozen metadata.
- Explicit admin retries reset recovery budgets while preserving signed transactions
  for unchanged claim inputs.
- Preserve mint-log capture around claim uploads and publication receipt logging
  around the shared rememes uploader when integrating the current backend.

## Backend Impact

- Changed services: `dbMigrationsLoop`, `claimsMediaArweaveUploader`, `api`.
- Required order: additive entity sync through `dbMigrationsLoop`, then the claims
  worker, then `api` for explicit retry-budget reset behavior.
- Database: nullable JSON `minting_claims.media_upload_state`; the bounded
  `claims-media-upload` schema scope includes this addition.
- Queue: existing payload and queue names retained; partial batch responses and
  per-message visibility changes support retry/handoff. The transport DLQ receive
  allowance is independent of the application failure budget. A Lambda Errors
  alarm surfaces initialization errors, crashes and hard timeouts.
- Shared uploader: optional compact source-backed state and caller cancellation;
  existing consumers retain embedded-source checkpoints and their defaults.
- No new services, frontend changes, OpenAPI changes or environment variables.

## Configuration

- Claims worker memory: 4096 MB; configured runtime remains 900 seconds.
- Lease: remaining invocation runtime plus 30 seconds, capped at 930 seconds.
- Queue visibility remains 930 seconds; controlled progress handoffs request two
  seconds and recoverable failures use approximately 10–123 seconds with jitter.
- Automatic recovery: ten recorded failures, at most 128 owned attempts and a
  24-hour lifetime. SQS redrive uses a 200-receive transport backstop.
- Metadata snapshots support up to 750,000 decoded bytes.

## Risks / Follow-Ups

- Stacked on #2587; retarget to `main` after that dependency merges. The
  repository runs the full backend build/test workflow and automatic CodeRabbit
  review only for `main` targets; verify those gates after retargeting.
- Source bytes must remain available at the existing URL. Changed bytes or invalid
  checkpoints stop publication rather than silently signing replacement uploads.
- Verify real end-to-end interrupted-upload recovery in staging before production
  rollout. Local persistence race coverage uses mocked database operations.
- Older workers cannot resume compact claims checkpoints. Complete active jobs with
  the recovery-aware worker, or disable consumption and preserve checkpoints before
  rollback. The nullable database column can remain in place.
