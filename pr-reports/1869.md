# PR Report: Fix release attribution and frontend production baselines

PR: https://github.com/6529-Collections/6529seize-backend/pull/1869
Branch: `agent-prxt/release-attribution-notes` -> `main`
Related PRs: https://github.com/6529-Collections/6529seize-frontend/pull/3504

## Summary

Deployment notifications once again show contributors, but attribution is now
bound to the exact authenticated Release Bus operation or documented manual
deployment evidence. Frontend production release notes also recognize both
approved production workflows and bridge safely between their histories.

## What Changed

- Labels an initiator as Release Train only when the allowlisted GitHub App
  supplies a valid train, operation, workflow, repository, environment, and
  service identity.
- Keeps manual initiators separate from contributor attribution and preserves
  mapped 6529 mentions plus safe unmapped fallbacks.
- Scopes Release Bus contributors to newly introduced or explicitly selected
  candidates, then narrows backend attribution to each service deploy plan.
- Derives manual backend contributors only when the selected PR head or merge
  SHA exactly equals the deployed SHA and the explicit manual service plan
  includes the deployed service. This rejects stale ancestor PRs while
  correctly covering shared source files used by multiple service artifacts.
- Bounds GitHub contributor-evidence requests so an unavailable evidence API
  cannot prevent the independently timed CI notification from being posted.
- Keeps the CI receiver deadline active through response-body consumption, so
  a peer that returns headers but stalls the structured outcome cannot hang the
  deployment workflow.
- Requires normal manual operations to provide an exact positive PR and rejects
  supplied contributor metadata; explicit internal or recovery operations use
  a no-PR opt-out that carries no attribution or release-note metadata.
- Keeps the generated deploy workflow and `ghdeploy` helper aligned so default
  deployments request a PR while `--internal` or `--recovery` selects the
  fail-closed no-PR path.
- Makes manual multi-service production deployments select and reuse one
  complete canonical service set for the PR, allowing intermediate services to
  hold and the final successful service to publish one grouped release note.
  Every service must deploy the same exact PR SHA; a newer descendant fails
  closed rather than receiving stale attribution.
- Filters automation identities and deduplicates human contributors
  case-insensitively. Release Bus, manual deployment, and release-note GitHub
  evidence accepts only accounts explicitly classified as users, rejecting
  organizations, Apps, bots, and unknown or missing account types.
- Renders valid unmapped manual initiators as GitHub profile links, reserving
  `unknown` for missing, invalid, or non-human actor identities.
- Preserves per-PR release-note contributors independently of CI-drop
  attribution.
- Selects frontend production baselines from an explicit allowlist containing
  the manual and Release Bus production workflows, including safe transitions
  in either direction, and stops history pagination as soon as a valid
  chronological baseline is found.
- Treats the most recent approved production run with the same deployed SHA as
  a terminal `already-deployed` skip instead of falling through to an older
  baseline and duplicating previously published changes.
- Validates the exact frontend production run, workflow path, branch, and
  deployed SHA while accepting both the live `in_progress`/null notification
  state and completed successful replay evidence.
- Rejects rollback, diverged, identical, or otherwise non-forward production
  comparisons with a terminal `invalid-range` outcome instead of generating or
  repeatedly retrying unsafe release notes.
- Exposes distinct outcomes for CI-drop acceptance, release-note eligibility,
  enqueue failures, generation skips, deduplication, and publication.
- Keeps immutable PR validation, bounded evidence pagination, Release Bus
  workflow selection, and release-note enqueue preparation in focused
  fail-closed helpers without changing their signed contracts.
- Covers rejection of mismatched open-PR heads and branches, stale merged PR
  ancestors, service plans that omit the deployed backend service, and explicit
  non-user contributor account types. A coupled run #15 contract test now
  carries the accepted alert through its queued message, cross-workflow
  baseline selection, PR-scoped contributor resolution, and release-note drop.

## Backend Impact

- Changed services: `api`, `releaseNotesGenerationLoop`, `releaseBus`
- API: Extends the signed internal CI alert contract with Release Bus operation
  identity and contributor evidence fields.
- DB/entities/migrations: None.
- Queues/events/integrations: Carries optional immutable Release Bus identity
  through release-note queue messages and reports best-effort enqueue outcomes.
- Manual deploy tooling: Requires the exact represented pull request so service
  contributor scope can be proven.

## Config / Env

No new secrets or runtime configuration. Existing GitHub workflow tokens gain
read-only pull-request access for immutable contributor evidence.

## Compatibility and Rollout

Deploy this backend PR before frontend PR #3504. The receiver accepts the
legacy contributor payload during that transition but deliberately omits
unverified contributors; after the frontend update, the full signed operation
evidence contract is used. The companion frontend notifier validates manual
run, workflow-file, branch, and deployed-SHA evidence while accepting the live
`in_progress`/null state of a successful notification step (plus completed
successful replays), so `manual-range` evidence reaches this receiver during
normal staging and production runs. No deployment, Release Bus control change,
notification replay, or historical release-note publication is part of this
PR.

## Release Notes

Frontend production releases can generate notes from either approved
production workflow without selecting staging or unknown histories. Every
approved frontend production run selects the most recent preceding successful
production run across both approved workflows, so Release Bus-to-manual and
manual-to-Release Bus transitions never skip intervening releases. Redeploying
the same frontend SHA is terminally skipped and cannot regenerate an older
release range.
