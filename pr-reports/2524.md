## Summary

From the identity switch-on (planned Wed 25 Nov 00:00 UTC), an identity on the 6529 chain can hold up to 16 wallets, so its consolidation key (the wallets joined by "-") can be longer than a subscription table's key column. The key-width migration widens those columns, but `subscriptions_nfts` and `subscriptions_nfts_final` stop at 666 characters and `subscriptions_redeemed` at 567. Identities of 14 to 16 wallets still don't fit, and before the migration no key over 200 characters fits. With this PR such a write is never truncated, never fails its batch and is never half made.

- A key is written only when every subscription table that stores it (balances, mode, nfts, nfts_final, logs, redeemed) can hold it, and only when the key has no earlier write waiting. Otherwise the whole write waits in a new table, `subscription_deferred_writes`. It is written in the writer's own transaction and logged with the alert code `SUBSCRIPTION_KEY_DEFERRED`.
- An identity is either fully on the subscription tables or fully waiting, so it is never on a list without a balance to charge. The daily build splits the list before it uploads it, so the published file and the final rows hold the same subscribers.
- The subscribe, count, mode and edition routes answer 400 for such a key, before any other check: "Subscriptions for identities with more than 13 wallets resume on <date>." The date comes from `SUBSCRIPTIONS_WIDE_IDENTITY_RESUME_ON`. Unset, the message says "after the identity switch", so set it (see Backend deployment). Nothing is queued for a person's change.
- Only replay has a flag. The deferral has none, and keys of 200 characters or less (every key today) take the old path unchanged.

## Backend impact

- **Writers.** The guard covers:
  - the daily build's final rows, automatic rows and their log lines;
  - top-ups: the balance and the top-up row wait together;
  - redemptions: one entry per token, so the balance, the redeemed row and the redeemed count move together;
  - the consolidation re-key: a re-key to a waiting key waits, and the old keys keep their rows;
  - the four write routes.
- **Coverage markers.** Markers for a key that doesn't fit, or that the process can't judge yet, are skipped; coverage is recomputed.
- **Widths.** Each writer reads the key column widths from `information_schema`, cached for five minutes, so it follows the migration as soon as it lands. A failed read keeps the last widths read. A process that has never managed to read them treats every column as 200 characters, and fails (to be retried) a write whose key is longer rather than queue it.
- **Queue.** `sequence` orders the entries. `dedupe_key` keeps one entry per write, so a re-run of the build or a retried batch replaces its entry under the key the write has now. Until dbMigrationsLoop has created the table, the "earlier write waiting" check reads the missing table as nothing waiting.
- **Replay.** `FEATURE_SUBSCRIPTION_DEFERRED_REPLAY` is off by default. Turned on, the top-up loop replays waiting writes whose key now fits every table, in order per key. Rollback: unset the flag; the queue keeps every write.
  - Each replay claims its entry inside the transaction that makes the write, so a write is made once and a failed one stays waiting.
  - A write that has to wait again is counted as re-queued.
  - Final-list rows and queued log lines (all from the daily build) are never written on replay: they are marked skipped, and the next daily build decides the card's list. An automatic row replayed this way has no log line. Replay is off by default.
  - Redemptions are replayed by the transactions loop, in its own redemption transaction. Their notices and coverage markers go out only after it commits.
- **Known limits.**
  - If the migration lands after identities grow past 4 wallets, those keys wait, and stay waiting until replay is turned on.
  - Losing the queue: each kind of entry can be derived again from its source (see the Rebuild part of the subscription key width guard section in `docs/architecture.md`). Redemptions are the exception. The legacy redemption loop is not idempotent, so setting its cursor back re-charges every later airdrop. A redemption can only wait if key columns are narrowed after its final row was written, or behind an earlier write of the same key.
  - After the migration, top-ups from 14 to 16 wallet identities sit only in the queue. Replay checks the key a top-up was queued under, so a top-up from an identity that later shrinks to 13 wallets still waits. A follow-up identity PR, which must merge after this one, credits every waiting top-up to the sender's identity when the identity tables are cut.
- **Tests.**
  - Unit: `subscription-deferred-writes.test.ts`, `subscription-key-width.test.ts`, `persist-top-ups.test.ts`, `consolidate-subscriptions.test.ts`, `subscription-coverage-dirty.test.ts`.
  - DB: `subscription-key-width.db.test.ts`. Each test sets the old and migrated widths itself, so it passes on the schema before and after the migration.
  - The DB tests cover: a 14-wallet identity held back whole; the 400 message; order per key; replay made once; a failed replay staying waiting; paging; dedupe; redemption replay only in the transactions loop; a lost redemption derived again from `transactions`; consolidation replay; top-up replay credited once; final rows and their log lines skipped on replay; a missing queue table; coverage.

## Backend deployment

Deploy `dbMigrationsLoop` first; it creates `subscription_deferred_writes`. Then deploy `api`, `subscriptionsDaily`, `subscriptionsTopUpLoop` and `transactionsProcessingLoop`. `delegationsLoop` (the consolidation re-key) and `ownersBalancesLoop` (coverage markers) also run the changed code and deploy with them. The API's read user (`DB_USER_READ`) needs SELECT on `subscription_deferred_writes`, because every subscribe, count, mode and edition change checks it; the loops' user needs read and write. Deploy this before or together with the key-width migration (#2522), which is due by Mon 23 Nov 10:00 UTC and by Tue 24 Nov 18:00 UTC at the latest. Before the identity switch-on (planned Wed 25 Nov 00:00 UTC), set `SUBSCRIPTIONS_WIDE_IDENTITY_RESUME_ON` to the date subscriptions move to chain identities (planned Thu 26 Nov 12:00 UTC), and update it if that date moves. Always set it: the fallback wording names the identity switch, which will already have happened. Alert on `SUBSCRIPTION_KEY_DEFERRED`. Leave `FEATURE_SUBSCRIPTION_DEFERRED_REPLAY` unset.
