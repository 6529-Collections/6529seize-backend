# PR Report: Detailed Desktop help

PR: [Backend #1998](https://github.com/6529-Collections/6529seize-backend/pull/1998)

Related: [Frontend #3947](https://github.com/6529-Collections/6529seize-frontend/pull/3947)

## Summary

Help6529 can answer 6529 Desktop onboarding and local-node recovery questions with concise replies and detailed procedures on request. It recognizes the former name, 6529 Core, as an input alias while using the current product names 6529 Desktop and 6529 Mobile in its answers. 6529 Mobile App Wallet questions retrieve the dedicated mobile corpus instead of the consolidation-wallet clarification.

## What Changed

- After reported Desktop installation, answer next-step questions with RPC activation and worker sync, without inventing account pairing requirements. Honor explicit answer-link lists for ordinary knowledge replies as well as Desktop replies; related paths cannot add unapproved footer links.

- Default to short replies and one diagnostic step; only explicit depth requests receive a full guide. Failed or oversized generation uses a short corpus fallback, preserving action warnings.
- Answer short app-discovery requests such as `is there an app`, `6529 app`, and contextual download/link replies with both official applications and one final Apps link. Use the frontend-authored Apps overview without model generation; keep wallet, troubleshooting, and third-party questions on their existing paths.
- Calculate progressive reconciliation starting blocks from the user-supplied local checkpoint and corpus-owned minimum, using 25%, 50%, 75%, then 100% of indexed blocks. Retain the range across short replies and require completed repair/recalculation before widening. Calculated templates are excluded from ordinary retrieval and never sent to model generation.
- Preserve checkpoint confirmations such as “yes both in sync” and “they reached that block”, including terse answers to the worker question. Carry the confirmed block comparison through recalculation so “done, still different” advances to reconciliation. Keep partial/uncertain reports from advancing and retain explicit transaction-reset guidance when requested.
- Separate definitions from setup and advance reported TDH repair steps without replaying the overview. Recognize node/reference mismatch symptoms and clarify ambiguous app context.
- Recognize natural mismatch wording such as `my node doesnt match 6529.io`, including apostrophe-free chat input.
- Preserve matching blocks in terse replies such as `same block different tdh and merkle`, and accept `no block is same` as a correction to the bot's different-block explanation. These replies advance to worker checks without restarting block comparison or prematurely suggesting repairs.
- Preserve authored fallback prose beginning “More info:” while discarding generated link-only footers.
- Append verified, relevant corpus links once in a final footer, preserving explanatory body text and sentence punctuation while removing empty URL wrappers.
- Desktop records without explicit approved links remain link-free, including older corpus records. Canonical-link fallback applies only to ordinary non-Desktop answers; native route metadata must not become a public footer link.
- Treat questions, uncertain reports, and negated completion reports conservatively, including plural-subject questions and unpunctuated questions such as “Which workers recalculated”; current corrections override prior acknowledgements. Missing dialogue stages in an older corpus fail closed rather than replaying a generic guide.
- Require forced Desktop stages to retain `desktop-core` eligibility; general app handoffs remain available only through normal topic retrieval.
- Filter Desktop retrieval to eligible Core and app-handoff records before ranking, then require substantive topic relevance so targeted TDH, transaction, NFT, wallet, and IPFS questions retrieve the intended procedure.
- Cold corpus-load failures use the processor technical-failure/refund path; only a loaded corpus without matching knowledge produces a no-source escalation.
- Normalize Mobile wallet aliases such as “mobile Core wallet” and “Core wallet on iOS” before retrieval so creation, import, connection, backup, password recovery, and deletion keep their requested action. Cross-platform wallet questions retain the storage clarification.
- Treat App Wallet, mobile wallet, and 6529 Mobile language as mobile product context, including questions that use the former Core name. Desktop TDH/Merkle shorthand and Desktop-versus-website comparisons and contextual follow-ups retain their validated scope.
- Fail closed when Desktop knowledge is unavailable. Existing app-download and device-connection records remain usable.
- Keep the production corpus frontend-owned; the backend snapshot is exclusively a regression fixture.

## Release Notes

Desktop support includes onboarding and recovery guidance without remote device inspection or control. Deploy this runtime first: it safely declines unsupported procedures until the new corpus arrives. Publishing the new corpus before upgrading the runtime can misroute generic wallet questions or truncate the new procedures. No Core release is required.

## Risks / Follow-Ups

Longer answers still share the existing model timeout; timeout fallback preserves a concise response for the current stage. Coordinate a rollback of the new corpus before reverting the runtime policy. Knowledge describes pinned Core behavior and must be reviewed when native controls change.

Full local TypeScript compilation is limited by missing API-only dependency declarations/modules in the available dependency tree (`js-yaml`, `@serverless/typescript`, `aws-serverless-express`, `swagger-ui-express`, and `@aws-sdk/client-managedblockchain`). The affected API files and manifests are unchanged from the PR base; no unrelated dependency fix is included.
