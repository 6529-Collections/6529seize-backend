# PR Report: Drop Forge Auto Launch Backend Requirements

Related PR: [Frontend #4207](https://github.com/6529-Collections/6529seize-frontend/pull/4207)

## Summary

Defines the backend scope and operational boundaries for unattended Drop Forge
launches. This is a requirements analysis only; no runtime behavior changes.
Full analysis: [backend requirements](../ops/workstreams/drop-forge-auto-launch/requirements.md).

## What Changed

- Documented versioned launch inputs, signing/permission/money boundaries,
  EventBridge triggering, sequencing, and recovery without duplicate airdrops.
- Specified durable wave reporting and `@dropforgers6529` alerts with manually
  supplied wave and recipient profile IDs.
- Identified synchronous EMMA phase preparation/finalization paths and required
  timeout investigation, safe retries, and consistent published results.
- Recorded acceptance scenarios and decisions to resolve before implementation.

## Backend Impact

No services, APIs, entities, infrastructure, or secrets change in this PR.
Future implementation likely needs entity sync, API contracts, and execution/
preparation/reporting workers; exact service scope follows implementation design.

## Config / Env

No configuration is introduced. Proposed future names are
`DROP_FORGE_OPERATIONS_WAVE_ID`, `DROP_FORGE_BOT_PROFILE_ID`, and
`DROP_FORGERS_6529_MENTION_PROFILE_IDS`; values will be supplied manually.

## Backend Deployment

None required for these documents. Runtime implementation and rollout are future
work; this PR deploys nothing.

## Risks / Follow-Ups

EMMA timeout causes remain unverified. Confirm signer provider, transaction
confirmation/fee policy, late-window behavior, airdrop categories/order, and
mention invocation permissions before coding. Pay Artist automation is excluded
pending a separate payout decision.
