# Encrypted messages on the relays: every delivery-service and report write as a signed record

[Backend PR #2545](https://github.com/6529-Collections/6529seize-backend/pull/2545)

## Summary

Every write of the encrypted-messaging delivery service, and every write of the report tables, becomes a record signed by 6529.io's orderer key and kept by the relays. Each stream is hash-chained. Reports are sealed to the moderation key, so the relays hold only ciphertext. The tables can then be rebuilt from empty from the relays alone, and checked against MySQL stream by stream.

A new one-minute loop publishes what waits, sends deletions when MySQL deletes or expires an item, checks the relays' stream heads, and reports the lag as metrics with alarms.

Drop reports also keep what they did for the reporter (`hide_drop`, `block_author`).

Everything is behind `E2EE_RELAY_MODE`, off by default. Rollback: set it to `off`. It stacks on #2542 (the rebuild check); #2523 and #2526 are merged.

## Backend impact

- **New tables** (additive): `e2ee_streams`, `e2ee_relay_outbox`, `e2ee_record_items`, `e2ee_relay_deletions`.
- **New columns:** `content_moderation_reports.hide_drop` and `block_author`, nullable. They are written in every mode, records on or off. The moderators' queue leaves them out.
- **Changed functions:** `api`, `dbMigrationsLoop` (tables and operator scopes), and the new `e2eeRelayPublishLoop`. While records are on, `GET /e2ee/me` gains `relay` (the caller's grant proofs in primary only; in mirror the list is empty) and `GET /e2ee/devices/{device_key}/inbox-status` gains `relay_head`, the inbox stream's head.
- **Modes:**
  - `off` (default);
  - `mirror`: MySQL commits first and the relays catch up in the background;
  - `primary`: not ready; it takes effect only with `E2EE_RELAY_PRIMARY_OPT_IN=true`.

## Backend deployment

1. #2542, the rebuild check (#2523 and #2526 are merged).
2. `dbMigrationsLoop` (full entity sync), then `api`.
3. Install the `E2eeRelayPublish<Stage>Deployment` policy first (replace `ACCOUNT_ID` with the account id), then deploy `e2eeRelayPublishLoop`.
4. The frontend PR.

**Team asks:**
- install the two deploy policies before the loop's first deploy;
- the orderer key, held by the team, with its public key published to the relays (`E2EE_ORDERER_KEY`, `E2EE_ORDERER_GRANT`, `E2EE_ORDERER_PUBLIC_KEY`), the site-reader key, and the moderation key pair;
- `E2EE_RELAY_URLS` (`<relay URL>`) and `E2EE_RELAY_NET`;
- the backfill dry run (counts only);
- the modes, planned and tied to the relays going live: off until then, then mirror, gated on `verify` answering `gate: "pass"` for every slice; primary not planned;
- any deletion of MySQL data waits for the owner's confirmation.

## Known limits

- The moderators' inbox is one stream: its head lock serializes report writes.
- Background publishes don't use the loop's per-run breaker. With a relay down, each write's background publish makes its own connection try; the loop sends what still waits within a minute.
- Moderation items rebuild with the moderators' decisions, not the AI's evidence: they read `PENDING` until the check runs again.
- The rebuild check's steps import test fixtures (`@/tests/fixtures`); they run only in the rebuild check.
