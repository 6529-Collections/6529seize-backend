# PR Report: Rebuild check: planned rows and columns, dated exemptions, and planned steps in the order check

PR: [#2582](https://github.com/6529-Collections/6529seize-backend/pull/2582)
Base: the column owners PR's branch (#2577); merges after #2577. main (#2542 with #2569) is in main.

## Summary

Some rows of a table can only be rebuilt once a later change lands, so the table differed on every run. A rebuilder can now declare those rows as planned, with the day the plan ends and the change that brings their source, and a plan can name the only columns that may differ on the rows it matches. A normal run names what the plans excuse and doesn't count it as a difference; a final run fails on every plan. An EXEMPT table can name the last day of its exemption, a planned rebuilder whose module isn't in the tree yet stays out of the order check until it is, and a step can order itself before or after another area's step that a later branch brings. Nothing outside the rebuild check and its docs changes.

## What Changed

- **Brought up to date** (`run/runner.ts`, `run/runner.rebuild.test.ts`). The branch takes #2577's head, which carries main (#2542 with #2569) and #2577's own changes since. Two files conflicted: `runner.ts` keeps this branch's imports and the step context import once; the end-to-end test's `run()` keeps both `today` and `absent`. The step needs and column owner tests that waited on `identity_chain_principals`, which main now creates, wait on the planned table `rebuild_self_check_absent`.
- **Planned rows** (`src/rebuild/manifest.types.ts`, `run/runner.ts`, `snapshot/table-snapshot.ts`, `stack/mysql-admin.ts`).
  - A rebuilder lists `plannedRows: [{ table, where, reason, until, change }]` for a table it writes. `where` is evaluated on the seeded rows; `until` is the plan's last day, `YYYY-MM-DD`; `change` names the change that brings the rows' source.
  - A matched seeded row the rebuild lacks is listed apart and doesn't make the table differ. An added row, a changed row and an unmatched missing row still differ.
  - Rows without a usable primary key are counted per identical row, so a plan excuses only as many copies as it matched.
  - A plan over another running rebuilder's partition, or a condition MySQL can't evaluate, fails the run.
  - A plan's condition runs on a connection of its own whose default is the run's main database, so a subquery can name other tables; the admin connection keeps no default database.
- **Planned columns** (`run/column-plans.ts`). A plan with `columns` lets the rows it matches come back changed only in those columns; every other column, and every other row, is compared. The rows must come back. A run refuses at its start a planned column the schema doesn't have or that sits in the primary key, and a table without a primary key free of volatile columns; it refuses a row both a plan of whole rows and a column plan match. The report gives each column plan its matched, differing and excused rows, per column.
- **Report and verdict** (`report/report.ts`, `run/verdict.ts`).
  - Every plan of the run's rebuilders is listed with the seeded rows it matched and how many the rebuild lacks.
  - A run notes a plan that matched nothing, one whose rows the rebuild writes now, and one whose table isn't in the schema.
  - Overdue plans and overdue EXEMPT tables go on the headline's and the status line's overdue line.
  - `--final` fails on every plan, and on every EXEMPT table with an `until`.
- **EXEMPT until** (`run/exempt-until.ts`). An EXEMPT table can name `until: 'YYYY-MM-DD'`. Past that day the run notes it as overdue; it doesn't fail, so a run doesn't turn red because the clock moved.
- **The run's day.** One per run, the day it started (UTC) unless `RunOptions.today` names one, recorded in the report.
- **Planned steps in the order check** (`registry-check.ts`, `step-code.ts`).
  - A planned rebuilder whose module isn't in the tree is left out of the read-order and column-order checks, and the run notes it with its tables. Its own reads are still checked, and an unknown id in `after` or `before` still fails.
  - A run decides once, per step, whether the module is there: a `.ts` or `.js` file spelled as the directory lists it, not through a link or a junction.
  - A final run fails on a step still marked planned whose code is here.
- **Cross-area order edges** (`registry-check.ts`). An `after` or `before` id naming another known area's step that isn't in the tree is an unresolved edge: noted, counted on the headline and the status line, with "did you mean" when a close id exists, and failed by `--final`. An unknown id of the step's own area or of no area, and an id of the other kind of step, still fail.
- **Registry** (`registry-check.ts`). It refuses malformed plans and planned columns (not plain, repeated, or owned by another rebuilder), an `until` that isn't a real day or sits on a table that isn't EXEMPT, a module path that is absolute, leaves the repo or names its extension, and an id shared by a seed and a rebuilder.
- **Docs** (`docs/rebuild-check.md`). All of the above, and that plans don't excuse probe answers.

## Risks / Follow-Ups

- **Merge order.** On top of #2559 (relay recordings) the registry words an unknown `before` id differently. Whichever lands second adapts the planned-step test's expected message and keeps #2559's `relayProblems` beside the new order-check arguments.
- **Plans hide absence.** A plan that matches more rows than intended hides their absence in a normal run. The report gives each plan's matched count, and a final run fails on every plan.
- **`where` is code.** It runs as written on the seeded database, as the harness's own account, and is reviewed like any other manifest code.
- **Column plans read the table twice.** A table with a column plan is read once more after the rebuild, to compare the changed rows column by column.
