# PR Report: Chat video previews

PR: [Backend #2140](https://github.com/6529-Collections/6529seize-backend/pull/2140)
Branch: `agent-prxt/chat-video-thumbnails` → `main`
Related PRs: [Frontend #4178](https://github.com/6529-Collections/6529seize-frontend/pull/4178)

## Summary

Accept a small poster captured on the device while a video uploads, store it before video completion, and generate backend JPEGs when no validated device poster exists. Chat displays either preview without fetching video before Play.

## What Changed

- Accept an optional bounded JPEG in multipart completion after ownership checks. Decode/re-encode to remove metadata, verify the pending upload, and write a separate `_device.jpg` before completing the original. Capture/storage failure uses the backend fallback without blocking posting.
- Share canonical upload-key eligibility between API storage and converter lookup. Skip device-poster requests for legacy keys and reuse the lookup client across warm invocations.
- Label fallback warnings with a stable event and failure stage, distinguishing validation, pending-upload lookup and poster writes while preserving video completion.
- Read and expand the existing MediaConvert template, preserving its input/audio selectors except for forcing `VideoSelector.Rotate` to `AUTO`, and retaining its HLS/MP4 outputs. When a validated device image is absent, append up to two JPEG captures, at the first frame and one second, with proportions bounded to 640 × 640 pixels, quality 80.
- Explicitly bind the two captures at one frame per second to the frontend's preferred sequence-1 key; sub-second clips retain sequence-0 fallback.
- Publish `renditions/drops/<author>/<name>/poster/<name>_poster.0000001.jpg` beside existing video renditions. The frontend derives this URL from the original upload URL and falls back to sequence 0 for existing/sub-second clips.
- Grant the existing Lambda role template-scoped `mediaconvert:GetJobTemplate`, in the configured bucket/MediaConvert region. Update the function after the policy exists. The shared job template is unchanged.
- Preserve S3 trigger and video extension filtering. No automatic old-video enumeration or replay.
- Reject duplicate or empty template output groups before submission. Retain stack-configured template/bucket/region through secret loading and warm invocations, and reuse a stable event token for immediate submission retries.

## Backend Impact

## Release Notes

Supported device uploads normally have a poster when posted; unsupported/failed attempts receive a preview after backend processing. Existing uploads do not receive thumbnails merely by deploying this code. A separately authorized replay can regenerate a selected old video's entire conversion, replacing its HLS/MP4 renditions and incurring conversion cost. No backfill was run.

## Risks / Follow-Ups

Device-poster validation and storage precede video completion to avoid racing
the converter and posting before the preview exists. Clients supplying a JPEG
can incur up to three seconds of extra S3 wait; timeout keeps backend fallback.
Legacy clients and clients without a captured JPEG do not make those S3 calls.

A validated device poster in S3 suppresses backend capture for that conversion
job. A later CloudFront delivery failure does not generate a replacement;
frontend retries only attempt image delivery. This is the accepted device-first
tradeoff that avoids duplicate previews. Public delivery must be verified during
rollout, and persistent CDN/object-access failures require repair.

The existing shared Lambda role gains template-read, device-poster read/write and pending-drop-upload read access. The API function uses an existing execution role whose association with that shared role must be verified during release; live credentials were unavailable. The converter remains a shared-media, staging-only service under the current deployment catalog. MediaConvert's token deduplication lasts one minute; later event redelivery remains possible. Any separately authorized backfill must protect existing renditions because replacement is not atomic.

The one-second capture avoids a black opening frame when content is visible by one second. Clips still black at that point can still have a black preview; already-generated black first-frame previews are not replaced automatically. Before release, verify long and sub-second conversions, both preferred and fallback JPEG delivery in chat, retained video renditions, and a rotated/portrait source with the account's configured AWS template and IAM permissions. Live AWS access was unavailable during implementation. See [the preview runbook](../docs/chat-video-previews.md).
