# PR Report: Targeted NFT metadata history recovery

PR: https://github.com/6529-Collections/6529seize-backend/pull/2260
Branch: agent-prxt/nft-history-targeted-replay -> main
Related PRs: https://github.com/6529-Collections/6529seize-backend/pull/2259

## Summary

Provide a bounded, reviewable way to audit and repair metadata history missed before sender-independent ingestion. Reuse the prerequisite PR's canonical event processing and reconciliation; keep historical recovery separate from the scheduled ingestion checkpoint.

## What Changed

- Manual dry-run manifests identify exact events, predecessor/result URIs, proposed metadata diffs, existing matches, successor corrections, settings-only updates, and unresolved failures.
- Replay explicitly disables schema synchronization and omits the scheduled checkpoint entity from its database context.
- A fixed finalized cutoff, block/event limits, and chain anchors define each window's coverage.
- Apply is disabled by default and requires a reviewed manifest digest plus a UUID job ID. Changed plans and unresolved failures are rejected.
- Corrupted stored receipts produce a controlled rejection without advancing progress.
- Durable job receipts bind the original proposal and atomically track progress with each history write. Retry and resume preserve already-applied events.
- The runbook covers complete historical coverage, staging acceptance, separate production authorization, cache/API/UI verification, and Meme #550's three expected metadata entries.

## Backend Impact

- Changed services: `dbMigrationsLoop`, `nftHistoryLoop`; the prerequisite also changes `api`.
- Deployment dispatch accepts the isolated `nft-history-replay` schema scope.
- Required service order: prerequisite event-table schema, replay-job schema, API reader, combined history Lambda.
- DB: additive `nfts_history_replay_jobs` entity; no deletion or reset of existing history or ingestion checkpoints.
- New services/queues/schedules: none. Replay is an explicit mode of the existing Lambda.
- Public API/client contract: unchanged.

## Config / Env

`NFT_HISTORY_REPLAY_APPLY_ENABLED` defaults to `false` in the history Lambda. Only separately authorized apply/resume operations require `true`; restore `false` after the approved recovery. Dry-run does not need this flag and writes no database state. The explicit `nft-history-replay` schema scope creates only the job entity.

## Risks / Follow-Ups

- Prerequisite #2259 is merged; this PR targets `main`.
- Production recovery requires the full historical audit and reviewed execution receipts before historical writes.
- Custom HTTPS metadata origins outside the prerequisite gateway policy and oversized metadata require explicit review; audit reports these failures without advancing.
- Unsupported execution paths/emitters/protocols, missing mint baselines, unavailable archive reads, and ambiguous mappings block affected windows and require explicit resolution.
- History or metadata changes can invalidate a paused job. Preserve its receipt, generate a fresh remaining-range audit, and obtain approval for the new digest instead of editing its cursor.
