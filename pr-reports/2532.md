# Charge each subscription airdrop exactly once, and distribution airdrops never

[Backend PR #2532](https://github.com/6529-Collections/6529seize-backend/pull/2532)

## Summary

The legacy subscription loop could charge a subscription airdrop twice, never charge it, or charge a free distribution airdrop. Each subscription airdrop is now charged exactly once, and distribution airdrops are not charged.

- **Charged twice.** The loop read the highest transaction block, then the airdrops above its cursor with no upper bound. The memes transactions loop could commit an airdrop in a new block between the two reads. That airdrop was charged in that run and again in the next one, wherever the wallet still had an unused edition of the card.
- **Never charged.** The block the loop recorded was the highest of the memes, gradients and memelab contracts. Each has its own transactions loop. A memes airdrop committed after another contract's higher block had been recorded sat below the cursor and was never charged.
- **Distribution airdrop charged.** The sum of a wallet's earlier airdrops came back from MySQL as a string, so `"1" + 1` made `"11"`. A wallet due two or more distribution airdrops of a card, sent in separate transactions, had every one after the first charged wherever it held an unused subscribed edition.

## Backend impact

- `redeemSubscriptions` reads the memes contract's highest block and reads airdrops only up to it. An airdrop in a later block is left to the next run.
- `validateNonSubscriptionAirdrop` adds the earlier airdrops as a number.
- MySQL tests show each bug before the fix and its absence after.
- Two read-only queries in the PR find past cases. The first nets, per card and airdrop wallet across subscriber keys, the charges recorded against the charges due, and gives the extra charges to refund and the airdrops never charged, with the key to put each right on. The second lists the airdrops behind each case. Both are tested on MySQL.

## Backend deployment

After the key-width guard (#2524), deploy `transactionsProcessingLoop`. There is no migration, flag or configuration. To roll back, revert the commits.
