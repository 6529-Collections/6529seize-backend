# Mint log: Drop Forge's own writes to the minting tables are logged

[Backend PR #2645](https://github.com/6529-Collections/6529seize-backend/pull/2645)

## Summary

Drop Forge's worker wrote three kinds of minting rows outside the mint log: a phase it prepares in the background (the subscriptions' phase columns, the phase's distribution rows and its merkle root and proofs), its finalize (the normalized rows), and the completion flags it mirrors into a claim's actions. Each is now logged as a service write (`authority: 'drop-forge'`) inside the transaction Drop Forge already runs it in, after Drop Forge's own locks. A rebuild from the log alone reproduces a card Drop Forge prepared, finalized and flagged.

It builds on #2536 (the mint log) and #2561 (the mint log's rebuild check steps), both in main.

## Backend impact

- **Changed functions:** `api` (the mint log's capture, and the signer transaction for Drop Forge's operations and recovery requests), `memesDistributionHandler` (phase preparation and finalize) and `dropForgeLaunchHandler` (completion flags, the signer transaction, the overdue-flag alert). No route or response changes, no migration. Other functions that bundle the mint log's recorder pick up one change on their next deploy and need none now: for a collaboration write inside a caller's transaction, a shadow failure's or a mismatch's alert is sent once that transaction commits.
- **With the mint log flags off**, Drop Forge runs as it does today: nothing is logged or held, each completion flag is written where it is mirrored, a flag that fails to write blocks the launch, and a launch completes in the pass that writes its last flag. The minting-claims API's code is as on main.
- **With the mint log on**, Drop Forge's writes read their kind's parts with FOR UPDATE and hold the mint log's one head until their transaction commits. In primary mode a mint log failure fails the job step, or undoes a held flag with its entry.
  - Completion flags are written at the end of the signer transaction, each under its own savepoint, at most two a pass.
  - A flag a pass misses (its write fails, or the pass has no room) doesn't block the launch. Its first miss posts one plain event in the Drop Forge reports wave, and every failure logs an error. A later delivery writes it, in any state: the launch keeps getting deliveries while a missed flag is unwritten, and manual transactions that fail to reconcile can't hold it back. Only missed flags are retried, so a launch's other missing flags stay as on main.
  - Every retry inserts the flag's row only where the claim has none. An admin unsets a flag by writing a row with completed false, and nothing deletes rows, so an admin's row stays as it is, and a flag set by hand stops its retries. A flag's first write upserts, as before; a deferred flag is marked missed at once, so its first actual write is already an insert-only retry.
  - On each delivery, a missed flag still unwritten 10 minutes after its first miss gets one alert with the mention, naming the claim action route and body to set it by hand, even when no pass can try the write (another launch holds the signer, or a manual transaction is unconfirmed).
  - A running launch isn't completed on a pass that still had a flag to write. Most often a receipt pass writes the last flag and the next reserve pass completes the launch, as on main; when the completing pass itself holds the last flag, the launch completes one pass later (the same delivery's next pass, or the next delivery, 15 seconds later). An admin's change to the same claim action made before the pass's flags take the mint log's head is overwritten by a flag's first write.
  - The phase's cache eviction runs after the job's commit, which waits for it.
  - Measured on a card with 4,000 allowlisted wallets, with the replay check on: one held flag adds 5.1 s to a signer pass (11 ms with the mint log off); a logged phase step holds the head 6.5 s, finalize 6.3 s (the benchmark's `[MINT_LOG_FLAG_TIMING]` line, run with `MINT_LOG_TIMING=1`).
  - A pass's flags share one lock-wait budget of 10 s for the head (`HELD_FLAG_LOCK_WAIT_SECONDS`), about 1.5 times the longest holder; the second flag gets what is left, at least 1 s. In primary mode a flag that gives up is retried; in shadow mode it commits unlogged with a `[MINT_LOG_SHADOW_FAILED]` alert, a gap the genesis before primary covers. Bigger cards give up more often.
  - A pass holds the signer for main's chain reads (each RPC up to 10 s) plus at most 21 s for the flags (10 s of waiting, 1 s for the second flag, 5.1 s of captures each). With every RPC at its deadline: a reserve pass that writes a launch's last flags about 51 s; a receipt pass about 61 s, or about 101 s after a nonce check; a Pay Artist receipt about 131 s or 171 s. When no other write holds the head, the flags add their captures alone, 2 × 5.1 s for two.
  - Meanwhile requests that take the signer row (retry, manual-transaction operations, recovery requests) wait behind any pass, the launch controls (pause, cancel, resume, arm) behind a pass on their launch, the Automatic launch switch behind a pass that has read the settings with a lock, and every logged mint write on any card for about 5.1 s per flag. A request through API Gateway that waits past its integration timeout (29 s by default) gets a 504; its change applies when the pass commits only if its own lock wait and Lambda timeout outlast the pass.
  - For a write inside the caller's transaction (all of Drop Forge's), a failed or skipped shadow entry's priority alert and an entry's mismatch alert are sent after that transaction commits, which waits for them; the error is logged at once.

## Backend deployment

`api`, `memesDistributionHandler` and `dropForgeLaunchHandler`, in any order (#2536 and #2561 are already in main).

Until this PR is deployed, the mint log can run in shadow mode; Drop Forge's writes are then missing from it, and the new genesis before primary covers them. The mint log's primary switch comes after this PR is in production.

Rollback: redeploy the previous three functions, in any order. The old code writes a running launch's missing flags with an upsert, so it overwrites an admin's set or unset made after a miss; a flag on a launch that isn't running stays unwritten until set by hand, and its event names it. Turning the mint log off has the same effect.

**Team asks:** a review by Drop Forge's owners, and a deploy at a time that suits Drop Forge's jobs. With the mint log flags off, Drop Forge runs as it does today (above).

Also: current reads for Drop Forge's writes only, both orders against an admin's logged write, held flags across a slow chain call, a held flag failing in shadow and primary mode, misuse refused, a primary-mode phase step whose head lock times out leaving no rows and no entry, the 10 s budget in both modes, two flags behind a held head (about 11 s, not 20), a flag waiting behind another card's logged write, and a benchmark (run with `MINT_LOG_TIMING=1`) of the phase step, finalize and one held flag on a card with 4,000 allowlisted wallets.
- `src/drop-forge/drop-forge-worker.db.test.ts`: with the mint log off, today's behaviour (the flag written in the completing pass, a failed flag blocking the launch). With it on: a flag failing in a completing pass, a receipt's pass and a reserving pass; in shadow and primary mode a cancelled launch's missed flags written two a pass, with an admin's unset row kept; an admin's unset after a first miss kept on a running launch and through an ended launch's manual branch; a flag written even when manual transactions fail to reconcile, alerting once if its write keeps failing; the overdue alert by age when another launch holds the signer and when a manual transaction is unconfirmed.
- `src/drop-forge/drop-forge-recovery.db.test.ts`: with the mint log on, a recovery whose flag fails still settles and releases the signer.
- Unit tests for the recorder, preparation, completion (one event per flag, the alert by age, insert-only retries, the per-pass cap), the held flags' budget and savepoints, dispatch (deliveries continue only for a missed flag with the mint log on) and the launch handler (the alert step before the passes).

## Known limits

- With the mint log on, a flag that fails on every pass keeps its launch getting deliveries, up to three passes each, every 15 seconds, until it is written or set by hand.
- In shadow mode, a flag that gives up on the head commits unlogged; retrying it on the next delivery as in primary mode is a follow-up.
- Every logged write captures the whole card, so a held flag costs seconds on a large card. The follow-up is to capture only the parts a write's kind may change.
- The rebuild check's seed writes Drop Forge's kinds through the API's paths only; a held-flag seed step is a follow-up.
- In shadow mode, once #2547's subscriptions switch names the identity tables, a phase split whose head lock timed out runs unlogged and can deadlock with a Drop Forge job. InnoDB rolls one back: the admin gets a 500 and runs the split again, or the job is retried. The unlogged split is a gap in the log; a new genesis (`6529 run mint-log:genesis -- --live --chain mint`) clears it, and the primary switch waits for that.
