# PR Report: iOS badge synchronization after notification reads

PR: [PR #1987](https://github.com/6529-Collections/6529seize-backend/pull/1987)
Branch: `agent-prxt/ios-badge-sync-on-read` → `main`
Related frontend PR: https://github.com/6529-Collections/6529seize-frontend/pull/3948

## Summary

Notification reads from any client now request an asynchronous iOS badge refresh through the existing push worker. Counts include every distinct profile registered to the device, preserving UserB's contribution when UserA reads and supporting zero after the final read.

## What Changed

- Queue a profile refresh after individual reads, mark-all-read, wave reads and mark-unread.
- Recalculate current totals from the primary database with existing push preferences and visibility filters.
- Coalesce shared-device requests, serialize normal iOS pushes and badge refreshes through a per-device Redis lock across token rotation, and retry failed work without sending partial or guessed counts.
- Send badge-only APNs payloads, including zero, with no sound, alert content or background wakeup.

## Backend Impact

- New services: None.
- Changed/planned services: `pushNotificationsHandler`, `api`.
- API: Internal queue handoff only; public contracts unchanged.
- DB/entities/migrations: No schema change; badge count queries explicitly use the primary.
- Queues/integrations: New `badge_refresh` message variant on the existing push SQS queue; existing retries/dead-letter queue and Firebase integration.

## Config / Env

No new configuration. The existing `PUSH_NOTIFICATIONS_ACTIVATED` API switch controls enqueueing. The worker's existing Redis connection must be enabled and available for iOS badge-bearing delivery; missing or failed coordination causes retries rather than an uncoordinated send.

## Backend Deployment

- Deployed API: None.
- Deployed Lambdas/services: None.
- Not deployed: `pushNotificationsHandler` and `api`, by request.
- Deployment order executed: None. Planned: `pushNotificationsHandler` first, then `api`, so the consumer understands refresh jobs before the API starts enqueueing them.
- GitHub Actions deploy run links or IDs: None.

## Risks / Follow-Ups

- Ordinary iOS alerts now require Redis coordination as well as badge refreshes; a Redis outage delays existing iOS alert traffic until retries succeed.
- Concurrent token groups for one device intentionally serialize through lock contention and SQS retries, including within one batch during token rotation. Repeated contention can reach the existing dead-letter policy.
- Legacy iOS casing is normalized on read. Unknown/null platforms preserve existing badges and require canonical registration before corrective updates can run.

- Verify an existing installed iPhone in foreground/background before rollout: 2 → 1, 1 → 0, no alert/sound, and rapid reads alongside a new push.
- APNs delivery is asynchronous and not acknowledged or guaranteed in order. Corrections expire immediately when the device is offline.
- Durable enqueue recovery is deferred: an outbox plus a reconciliation consumer requires a separate storage/worker rollout. Queue handoff is best effort after persistence, without an outbox. A failed enqueue or interrupted process can leave a stale badge until a later read/unread or normal push.
- The companion frontend cleanup uses profile-scoped, server-confirmed reads. Android visible pushes now carry a versioned profile/notification/wave tag so existing native tray APIs can identify them even without FCM custom extras. Legacy untagged entries remain untouched; Android launcher numeric behavior is not guaranteed.
- Rollback the API producer before the worker, allowing queued refresh jobs to drain. See [mobile badge documentation](../docs/mobile-badge-sync.md).
