# PR Report: Mobile badge synchronization and logout cleanup

PR: [PR #1987](https://github.com/6529-Collections/6529seize-backend/pull/1987)
Branch: `agent-prxt/ios-badge-sync-on-read` → `main`
Related frontend PR: https://github.com/6529-Collections/6529seize-frontend/pull/3948

## Summary

Notification reads from any client now request an asynchronous iOS badge refresh through the existing push worker. Counts include every distinct profile registered to the device, preserving UserB's contribution when UserA reads and supporting zero after the final read. Native logout also revokes the selected profile or entire installation without signing out other devices, and asynchronously corrects its badge.

## What Changed

- Queue a profile refresh after individual reads, mark-all-read, wave reads and mark-unread.
- Recalculate current totals from the primary database with existing push preferences and visibility filters.
- Coalesce shared-device requests, serialize normal iOS pushes and badge refreshes through a per-device Redis lock across token rotation, and retry failed work without sending partial or guessed counts.
- Send badge-only APNs payloads, including zero, with no sound, alert content or background wakeup.
- Add installation-authenticated logout with profile/device deletion or a device-wide sweep, including stale registrations missing from the client account list. Revoke only supplied native refresh sessions.
- Validate installation secret/revision pairs before registration and serialize concurrent creation and updates with an exclusive database row lock.
- Persist hashed installation ownership, monotonic revision and the latest token/platform. Fence stale registrations, make deletion retries idempotent, and retain a zero-badge delivery target after final logout.
- Coordinate Android final-recipient validation with logout through the device Redis lock, preserving launcher-dependent badge behavior.

## Backend Impact

- New services: None.
- Changed/planned services: `dbMigrationsLoop`, `pushNotificationsHandler`, `api`.
- API: Add `POST /push-notifications/installations/revoke`; registration accepts installation secret/revision. Regenerate OpenAPI models and routes.

The worker's existing Redis connection must be enabled and available for native logout and both iOS/Android alert delivery; missing or failed coordination causes retries rather than an uncoordinated send.

## Risks / Follow-Ups

- Ordinary iOS/Android alerts and native logout now require Redis coordination as well as badge refreshes; a Redis outage delays native logout and alert traffic until retries succeed.
- Token groups for one device run sequentially within each refresh batch; distinct devices run concurrently. Cross-worker contention still retries through SQS and can reach the existing dead-letter policy.
- Legacy iOS casing is normalized on read. Unknown/null platforms preserve existing badges and require canonical registration before corrective updates can run.

- Verify an existing installed iPhone in foreground/background before rollout: 2 → 1, 1 → 0, no alert/sound, and rapid reads alongside a new push.
- APNs delivery is asynchronous and not acknowledged or guaranteed in order. Corrections expire immediately when the device is offline.
- For notification reads, durable enqueue recovery is deferred: an outbox plus a reconciliation consumer requires a separate storage/worker rollout. Queue handoff is best effort after persistence, without an outbox. A failed enqueue or interrupted process can leave a stale badge until a later read/unread or normal push.
- The companion frontend cleanup uses profile-scoped, server-confirmed reads. Android visible pushes now carry a versioned profile/notification/wave tag so existing native tray APIs can identify them even without FCM custom extras. Legacy untagged entries remain untouched; Android launcher numeric behavior is not guaranteed.
- Native logout retains a secure client outbox until deletion and queue handoff succeed. Offline pushes can continue until reconciliation; clearing app storage can lose pending work.
- Legacy installation claiming requires the supplied token to match all existing device rows. Conflicting legacy tokens or lost credentials require verified operator assistance; device ID alone cannot authorize a sweep. Claimed installations reject older frontend registrations without proof.
- Keep the schema on rollback. Roll back the frontend before the API producer, then drain jobs before the worker. See [mobile badge documentation](../docs/mobile-badge-sync.md).
