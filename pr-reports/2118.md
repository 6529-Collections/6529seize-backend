# Preserve GIF animation in CDN previews

PR: [Backend #2118](https://github.com/6529-Collections/6529seize-backend/pull/2118)

Related: [Frontend #4099](https://github.com/6529-Collections/6529seize-frontend/pull/4099)

Large GIFs can exceed the legacy full-animation memory estimate and receive a
static preview. The new `_gifv2` derivative contract processes individual frames
within explicit resource limits and preserves frame timing and looping. It can
reduce output resolution to preserve the complete animation. Already-fitting,
eligible GIFs retain their original bytes, avoiding re-encoding inflation.

New derivative keys bypass cached static previews. Legacy paths remain compatible;
the frontend can fall back to them and offers explicit original playback. Source
uploads and existing derivatives are unchanged. Architecture and media-contract
documentation describe the limits and recovery behavior.

the new keys.

## Risks / Follow-Ups

Verify duration and peak-memory headroom on the actual Lambda runtime before
completing rollout; local native conversion is not a production resource
measurement. Limits can reject expensive GIFs, and legacy fallback previews can
still be static. Roll back frontend URL selection first if necessary.


Follow-up hardening validates GIF delay metadata, bounds processing by Lambda
remaining time after source spooling, and retains upload/cleanup headroom. The
successful derivative cache policy matches the legacy path. Fresh upload UUIDs
avoid source replacement collisions; out-of-band replacement under an unchanged
key still requires derivative regeneration and CDN invalidation. The deployment
catalog has no staging target for this worker, so actual runtime validation must
precede enabling frontend consumers.

Processing deadlines remain retryable operational failures rather than cacheable
input rejections. GIF source decoding retains the legacy tolerance for recoverable
data while keeping the animation and resource limits.
