# PR Report: ETH price recovery contention

PR: https://github.com/6529-Collections/6529seize-backend/pull/2121
Branch: `agent-prxt/eth-price-recovery-contention` → `main`
Related PR: https://github.com/6529-Collections/6529seize-backend/pull/2120

## Summary

Historical recovery could time out, continue issuing repairs under contention,
and subsequently fail the live-price insert. The collector now commits the live
quote first and stops historical work after a database failure.

## What Changed

- Historical batches start at at most one hour. Older larger Redis limits are
  capped; smaller learned limits and timeout reductions remain effective.
- Transaction USD corrections use persisted price intervals and indexed date
  ranges instead of repeated historical-price subqueries per transaction.
- Mint candidates come from affected transactions. Only their existing mint-stat
  rows are locked; full-token USD totals remain atomic with price/transaction
  correction.
- One structured collector error includes live-save status, failed ranges, and
  safe database-stage diagnostics. The same error is logged and thrown for
  handler deduplication; invocation failures and infrastructure alarms remain.

## Backend Impact

Only `ethPriceLoop` changes. No database schema, entity, migration, API, frontend,
new service, or configuration change. Existing writer guards from #2120 remain.

## Backend Deployment

Not deployed by request. Deploy `ethPriceLoop` after confirming the #2120 writer
versions have deployed and old invocations drained, reserved concurrency is one,
and Coinbase egress is permitted. Preserve the held production release-note
batch for #2120 when completing the original rollout alongside this follow-up.

## Risks / Follow-Ups

Check the previously failing range in staging before production promotion.
Live-first ordering protects the committed quote from a subsequent rollback,
but cannot remove external locks or prior database cleanup. A one-hour candle
batch is not a bound on transaction count or full-token mint aggregation work.
A single 32-hour gap normally takes about 32 successful scheduled recovery runs;
smaller learned batches, omitted candles, or failures require longer. Use the
new stage diagnostics and read-only database lock/query-plan evidence if
contention persists.
