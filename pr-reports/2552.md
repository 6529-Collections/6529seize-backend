# PR Report: Read a wallet's TDH at the latest TDH block

PR: [#2552](https://github.com/6529-Collections/6529seize-backend/pull/2552)
Base: main

## Summary

`GET /api/tdh/wallet/{wallet}` answered 404 for any wallet with rows for more than one block in the wallets TDH table. The lookup returned a row only when exactly one matched, and the table keeps a row per wallet per block: a full TDH write deletes only its own block's rows, and nothing prunes earlier blocks. The route now reads the wallet's row at the newest block in `tdh_blocks`, the block the other wallet TDH reads already use.

## What Changed

- `src/api-serverless/src/tdh/api.tdh.db.ts`: `fetchTDH` takes an optional `{ atLatestTdhBlock }`, which adds `block = (select max(block_number) from tdh_blocks)`. Without it, the lookup is unchanged.
- `src/api-serverless/src/tdh/api.tdh.routes.ts`: the wallet route passes `atLatestTdhBlock: true`. A wallet with no row at the newest block gets 404, as a wallet with no TDH does.
- The consolidated route keeps the lookup without the filter. Its table holds one row per consolidation key.
- Tests: a new DB test (`api.tdh-fetch.db.test.ts`, 5 cases: two days give the newer day's row; no row at the newest block finds nothing; the consolidated lookup as before; the one-row rule without the filter; nothing before the first recorded block) and two cases in `api-tdh-routes.test.ts`.

## Backend Impact

**Deploy:** `api` only. No schema change, no flag, no loop change.

**Live behaviour.** Wallets whose rows span several blocks get their row at the newest block instead of 404. A wallet with exactly one row that is not at the newest block now gets 404, as the other wallet TDH reads already treat it.

**Other services.** None.

## Config / Env

None.

## Rollback

Revert the PR. Nothing to undo in data.

## Risks / Follow-Ups

- **A rerun before the day's full run.** If a delegation change reruns TDH after midnight and before that day's full run commits, the newest `tdh_blocks` row has only the rerun's wallets; other wallets answer 404 until the full run commits, as the profile collected reads already show no TDH then.
- **Production.** Not checked. This PR doesn't claim the 404 shows in production; whether production wallets have rows for more than one block can be checked separately.
- **With TDH from the chain (#2525).** The two change no file in common. The chain-mode write also deletes only its own block's rows, so the fix applies there as well.
