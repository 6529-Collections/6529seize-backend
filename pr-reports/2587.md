# Unified backend Arweave recovery

[Backend PR #2587](https://github.com/6529-Collections/6529seize-backend/pull/2587)

Recurring NFT failures exposed inconsistent Arweave recovery: metadata and previews could stop at one failing gateway while another served the same transaction. Other consumers had separate gateway lists, native upload loops, or HTTP checks outside their fallback callbacks.

The backend now uses one active gateway registry, bounded content recovery, a shared SDK client and one upload engine extracted from TDH. Read callbacks complete HTTP/body/content checks before an attempt succeeds. Signing keys stay local; gateway changes reuse the signed transaction, original bytes and chunk proofs. Durable uploads retain their existing checkpoint format and resume the saved transaction. Each gateway registers that same signed header before resumed chunks; checkpointed progress remains a contiguous prefix. Native gateway responses, including resumed status probes, are capped at 64 KiB and bound to the upload session deadline, and CMS byte-policy rejection stops further attempts while preserving the API error contract.

Preview downloads retain a 15-second header timeout, a maximum 90-second overall budget and the 120-second Lambda timeout. Arweave attempts get at most 30 seconds; body inactivity gets ten seconds by default. The optional `NFT_LINK_MEDIA_PREVIEW_BODY_IDLE_TIMEOUT_MS` setting belongs to the preview worker. Other operation budgets and the complete caller inventory are in [Arweave recovery](../docs/arweave-recovery.md).

A typed size rejection is persisted and uses the existing source/size-policy cooldown without an individual operational error. Cached previews and completion fencing remain intact. This does not increase a size limit or assume a production size override. Exhausted provider failures and timeouts still produce operational errors. The `seizeAPI` `API_POLICIES` fingerprint is outside this change.

## Backend service impact

The affected deploy units are:

- `nftLinkRefresherLoop`, `nftLinkMediaPreviewLoop`
- `nftsLoop`, `nftHistoryLoop`, `s3Uploader`, `tdhHistoryLoop`
- `claimsBuilder`, `claimsMediaArweaveUploader`
- `rememesLoop`, including its S3, metadata-refresh and file functions
- `subscriptionsDaily`, including its bundled coverage reconciliation function
- `overRatesRevocationLoop`, `signedRecordLogLoop`, `royaltiesLoop`, `teamLoop`, `tdhLoop`
- `api`

### Planned initial production batch

The initial batch contains five deploy units:

- `nftLinkMediaPreviewLoop`
- `nftLinkRefresherLoop`
- `claimsBuilder`
- `claimsMediaArweaveUploader`
- `api` (Lambda `seizeAPI`)

The remaining 11 affected units are deferred to subsequent deployments: `nftsLoop`, `nftHistoryLoop`, `s3Uploader`, `tdhHistoryLoop`, `rememesLoop`, `subscriptionsDaily`, `overRatesRevocationLoop`, `signedRecordLogLoop`, `royaltiesLoop`, `teamLoop`, and `tdhLoop`.

`dropForgeLaunchHandler` and `memesDistributionHandler` do not introduce Arweave reads or uploads requiring migration in this change, so they are not added to this batch. Drop Forge uses the metadata reference already published by the claims workflow; its own rollout requirements remain separate.

No API schema, database schema, queue or event contract changes are required. There is no mandatory cross-service deployment order. Suggested verification order is the NFT workers, other read consumers, upload consumers, then API. Rollback uses the preceding service code; checkpoint compatibility is retained.

## Operational follow-through

After an independently authorized rollout, verify processing outcomes for the previously failing NFT sources: successful metadata and `READY` previews, or an accurate persisted policy rejection. Compare a full day of success and terminal-failure rates against similar traffic before assessing Discord volume. Successful alternative downloads should be visible as recoveries, while final failures remain visible as failures.

Persisted claim-media URLs keep the canonical Arweave location independently of the preferred read gateway. History metadata retains its overall deadline for IPFS as well as Arweave; a missing primary animation can still use its metadata image after alternate gateways fail. SDK status reads validate confirmation objects, and the buffered SDK adapter rejects web streams before fetching.

Gateway recovery cannot retrieve content absent from every provider. Broader persisted retry backoff and size-limit increases remain separate decisions.

Caller-supplied transaction tags, including subscription opening/history discovery tags, are signed before publication and retained unchanged across gateway retries and saved resumes.

Unposted one-chunk file uploads, including saved resumes, retain the inline signed-data submission path; ambiguous header acknowledgements and known-posted header-only progress require separate chunk acknowledgement. Checkpoint waits stop at the session deadline, while CMS keeps pending persistence fenced by its existing reservation token. Raw-mode recovery preserves the stored bytes of manifests across gateways using canonical raw endpoints, and SDK status validation supports buffered text and query-bearing paths without changing returned response data.

Chunk progress advances only after HTTP 200. A gateway that loses its registered data root receives the same signed header again; stale concurrent responses cannot discard a newer registration. Resume probes distinguish HTTP 202 from a validated HTTP 200 confirmation. Gateway URL normalization preserves manifest paths on transaction subdomains, and SDK validation applies equally to endpoints with a leading slash while honoring caller retry vetoes.
