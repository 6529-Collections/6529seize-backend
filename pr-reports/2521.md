# PR Report: Recovery when push device and WebSocket rows are gone

PR: [PR #2521](https://github.com/6529-Collections/6529seize-backend/pull/2521)
Branch: `claude/native-push-recovery` → `main`

## Summary

If the push device, installation, logout-fence or WebSocket connection tables are emptied or lost, installed apps can't recover today:
- the native app gets 409 on every registration;
- a queued logout can block registration for good;
- open sockets stay silent until API Gateway closes them.

Two flags, both off by default, let the app register again at its next start and let sockets reconnect. With the flags unset, behaviour is unchanged.

## What Changed

- `PUSH_INSTALLATION_ADOPT_REVISION=true`:
  - A registration that claims an unowned installation takes the client's revision when it is above the stored one (zero, or a surviving fence). A fence still refuses any lower revision.
  - A logout for an unowned installation, or one claimed in the same request by legacy token proof, may skip revisions. An early logout still needs a live native session; re-login proves it through the existing reconciliation sessions.
  - A token cleanup with no fence for its credential, no session proof and no registration row holding its token is acknowledged and writes nothing.
    - The transaction rolls back; an existing installation row keeps its last token.
    - The answer doesn't depend on other rows, so a token cleanup reveals nothing about the device. Logout errors still differ, as before.
    - The cleanup path keeps its exact-next-revision rule.
  - Installations the server holds keep the exact-next-revision rule and every credential check.
- `WS_CLOSE_UNKNOWN_CONNECTION=true`:
  - A `SUBSCRIBE_TO_WAVE` or `SET_OPEN_WAVE` whose update reports no matched row reads the row by primary key from the writer.
  - Only if the row is missing does it close the transport and answer 410, as `AUTHENTICATE` does.
  - PING stays free of database reads, and database errors stay plain 500s.
- Docs: `docs/mobile-badge-sync.md` ("After the push tables are emptied") and `ops/docs/operations/websocket-delivery.md` ("Connection rows that disappear").

## Config / Env

- `PUSH_INSTALLATION_ADOPT_REVISION` and `WS_CLOSE_UNKNOWN_CONNECTION`: optional; unset or anything but `true` means off.
- Set them where the API reads its configuration: the shared runtime secret when the API loads secrets, otherwise its runtime environment.
- Each API instance reads them once when it starts. Redeploy `api` to apply a change everywhere at once.
- Rollback: unset the flag and redeploy `api`. Nothing either flag wrote needs undoing.

## Risks / Follow-Ups

- Never empty these tables on purpose. After a wipe, any signed-in user who knows a device ID can register it first with their own credential. The phone's registrations are then refused as an invalid credential, and the app has no way to recover on its own. This race exists with or without the flag.
- If `ws_connections` must be emptied, close every listed connection through the gateway first; rows deleted under open sockets can't be found afterwards.
- Older clients that suppress normal-close reconnects get no frames until reload after a 410 close, the same as with today's silent socket.
- An adopted revision can't tell a stale registration from before a lost logout from a current one. Only state the server lost is affected, and a surviving fence still refuses older revisions.
