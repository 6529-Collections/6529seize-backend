# Read the key-width guard's waiting writes with a locking read

[Backend PR #2539](https://github.com/6529-Collections/6529seize-backend/pull/2539)

## Summary

Follow-up to #2524, which is merged. The key-width guard checks whether a key already has a write waiting, so one key's writes keep their order. Until this PR, writers make that check with a plain read inside their own transaction, which returns the transaction's snapshot. A write that another process queued for the key after that snapshot would be missed, and the writer would go ahead of it. Writes would apply out of order or wait behind a later one; nothing would be lost or made twice. This can't happen today, because no key that fits has a write waiting. It becomes possible once such keys exist and their writes replay, so the fix goes live before the identity switch-on.

## Backend impact

- Inside a writer's transaction (top-up, redemption, consolidation, daily automatic subscriptions) the check reads `FOR SHARE`: it sees the latest queue and holds back a new entry for the key until the writer commits. The API's check and the daily final-list split run outside a transaction and keep a plain read, so no locking read goes to the read pool.
- MySQL tests show a writer seeing a write queued after its snapshot, and a write queued during the writer's check waiting for it. Both fail without the locking read. Unit tests check that the API's check never locks.
- A process queueing a write can now wait for a writer's transaction to commit. After the identity switch-on, such a write can reach the lock-wait timeout behind a long redemption run, and two loops queueing in the same gap at once can deadlock; either way that loop retries on its next run.

## Backend deployment

With #2524 or after it, deploy `api`, `subscriptionsDaily`, `subscriptionsTopUpLoop`, `transactionsProcessingLoop` and `delegationsLoop`. There is no migration, flag or configuration. To roll back, revert the two commits.
