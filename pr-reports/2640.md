# PR Report: The TDH-only identities record: one format, written and read with its sha256

PR: [#2640](https://github.com/6529-Collections/6529seize-backend/pull/2640)
Base: `main`

## Summary

Identities without a handle got random profile ids from 6529.io before the identity switch-on: TDH-only identities, and rows made for wallets that had none. A profile id never changes once issued, and a rebuild from empty can't derive a random one. So these rows and their address keys are recorded right before the identity mirror's first run, and a rebuild reads them later, pinned by sha256. This PR adds the one format both sides use: a function that writes the record and one that reads it back and checks it. Nothing calls them yet.

## What Changed

- **`formatTdhOnlyRecord(rows, keys)`** writes the record's two files and their sha256.
  - Identities: every row with no handle whose profile id isn't a chain principal, as `consolidation_key, profile_id, primary_address, tdh, rep, cic, level_raw`.
  - Address keys: those rows' `address_consolidation_keys`, as `address, consolidation_key`.
- **`parseTdhOnlyRecord(identitiesTsv, keysTsv, { identitiesSha256, keysSha256 })`** checks both files against their pinned sha256 and against everything the format promises, then returns typed rows. On the first thing that's off it throws `TdhOnlyRecordError`, naming the file and the line.
- **The format is what the MySQL client writes in batch mode** (`mysql --batch --raw`), so a read-only query and a snapshot in code give the same bytes:
  - tab-separated, UTF-8 without a BOM, LF line ends and a final LF, one header line;
  - for no rows the client writes nothing, so an empty file reads as an empty record;
  - rows sorted by consolidation key and keys by address, in byte order;
  - lowercase keys and wallets as stored, decimal integers, and `NULL` for a missing profile id.

## Backend Impact

**Deploy:** none. Two new files under `src/identity-chain-mirror/`. Nothing imports them yet, so no deployed unit's bundle changes. No route, table, column, loop, schedule or flag.

**Live behaviour.** Unchanged.

**Other services.** None. The identity rebuild check's seed, in a later PR, uses the parser to put these rows back before it replays the identity mirror.

## Risks / Follow-Ups

- **A real record the parser refuses.** It refuses only values outside the format, such as a profile id with characters outside `[0-9A-Za-z_-]` or a number past 2^53-1. The record's files are kept as taken and pinned by sha256, so such a case is fixed by widening the check, without taking the record again.
- **Tests:** `tdh-only-record.test.ts` (15 tests, no database) covers:
  - one record's two files pinned to their sha256;
  - empty and header-only records;
  - round trips of generated rows (format, parse, format again to the same bytes);
  - each refusal:
    - a sha256 that isn't the pinned one;
    - a byte order mark, a carriage return or no final line feed;
    - another header or a wrong field count;
    - rows out of order or repeated;
    - a number, wallet or key it can't read, `-0` and a number past the safe range included;
    - an address key with no row or outside its row's key, and an empty keys file next to recorded rows;
    - a primary address on two rows.

  `tsc --noEmit` has no errors, and ESLint and Prettier are clean on both files.
