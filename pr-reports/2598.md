# PR Report: Rebuild check: a declared row key, and volatile columns scoped by a condition

PR: [#2598](https://github.com/6529-Collections/6529seize-backend/pull/2598)
Base: the planned rows PR's branch (#2582); merges after #2582

## Summary

Some tables' primary key is an auto-increment number a rebuild gives anew: `waves.serial_no` for the waves the chain makes, `waves_metadatas.id`. The only way to stop that number failing the comparison was to make the column volatile on every row. The rows were then keyed by their hash, so a column plan could no longer find them, and every row's number went unchecked, the imported rows' included. An INDEX table can now declare a `rowKey`, and a volatile column can name `where`, so it is left out only of the rows the condition matches. Nothing outside the rebuild check and its docs changes.

## What Changed

- **Brought up to date.** The branch takes #2582's head, which carries #2577 and main up to #2636. No file conflicted.
- **A declared row key** (`manifest.types.ts`, `snapshot/table-snapshot.ts`, `run/row-keys.ts`).
  - `rowKey: [...]` on an INDEX table names columns that are exactly one of its UNIQUE indexes, all NOT NULL. The comparison keys the table's rows by them, so a row whose number moved is the same row, changed. Planned rows, column plans and owned columns find their rows by it too.
  - The registry refuses a `rowKey` on another class, with no columns, with a column twice, or holding a volatile or exempt column.
  - At its start a run fails when a column isn't spelt as the schema spells it, when no UNIQUE index has exactly those columns, or when one may hold NULL. It notes a `rowKey` that is the primary key.
- **A volatile column scoped by a condition** (`snapshot/table-snapshot.ts`, `stack/mysql-admin.ts`).
  - `where` leaves the column out only of the rows it matches. Each side reads the condition beside its rows and takes a row as matched where a WHERE would.
  - A row matched on one side only keeps the column on the other, so it shows as changed.
  - The table needs a row key free of the column, and the condition can't name its own column. A run fails at its start on either, and on a condition MySQL can't read. A final run treats a scoped volatile column as any volatile one.
- **The report** lists the tables keyed by a declared row key, and each scoped column with its condition and its counts.
- **Code-unit order** (`src/rebuild/code-units.ts`). `compareCodeUnits` sorts by UTF-16 code unit, the same on every machine, and the new MySQL test sorts with it.
- **Docs** (`docs/rebuild-check.md`). Both features, beside volatile columns and column plans.

## Risks / Follow-Ups

- **CI evidence.** The backend's PR checks (`on-pull-request.yml`) run only on a PR whose base is main, and #2582's checks cover #2582's own head, without this PR. Once #2582 merges, this PR's base moves to main, and its full checks run on its final tree before it merges.
- **One condition per column.** A column volatile on two kinds of rows needs one condition covering both.
- **Rows matched on one side only** show as changed. That's intended, but it can surface a difference the plain volatile column used to hide.
- **Older sorts.** Ten older sorts in the rebuild check's code still use `localeCompare`, and six in its tests. They move to `compareCodeUnits` in a follow-up. One orders a recording's query parameters into its keys, so a recording made under another locale could miss on replay.
