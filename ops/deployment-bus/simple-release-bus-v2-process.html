Release process

The feature or fix has been written. It is now ready to enter the deployment process.
Someone tells the agent what to deploy and where

Tell the agent what feature to deploy. Say whether it includes the frontend, backend, or both. Then say how far to go: open PRs only, staging, or production.

For example
  • Review only: “Open PRs for the new search page and API. Do not deploy them.”
  • Frontend only: “Deploy the new search page to staging.”
  • Backend only: “Deploy the new search API to staging.”
  • Frontend and backend: “Deploy the new search page and API to staging.”
  • Staging and production: “Deploy the new search page and API to staging, then production.”

Frontend and backend can be handled separately or together. Production needs a version that passed staging. It starts as a separate action.

The agent checks the chosen changes
  • Frontend code → deploy the frontend
  • API code → deploy api
  • Database change → deploy dbMigrationsLoop first
  • Loop code → deploy that loop
  • Shared code → deploy every service that uses it

This gives the agent a first list of what may need to be deployed.

The agent gets each PR ready for review
  • Adds the completed code for that repository
  • Explains what changed and why
  • Lists the checks that were run
  • Notes important risks
  • Lists what must be deployed and in which order

Example: deploy dbMigrationsLoop first, then deploy api.

Each PR records its own services and deployment order.

The agent works through a review loop
CI and reviewers check the latest PR version ↓ The agent handles valid findings ↓ The agent runs checks and pushes the fixes ↓ CI and reviewers check the new version ↓ Repeat until the PR is ready

The PR is ready when required CI passes, required approval is present, and no blocking findings remain.

Invalid review suggestions can be explained instead of implemented.

If a blocker remains, the PR stays in this review loop. The agent reports the exact reason and asks for help when needed.

The agent makes the final plan from the reviewed PRs
  • Which backend services to deploy
  • Which services must go first
  • Which services can deploy together

Review fixes may change the plan, so it is finalized after review. Frontend PRs do not need a backend service plan.

The staging lane is checked before deployment

The status check reports both lanes. This step uses staging.

  • Staging ON → use Release Bus
  • Staging OFF and manual fallback allowed → use the safe manual deployment process
  • Status missing, unclear, or unsafe → stop and report the problem

The result decides how staging may be deployed.

Release Bus checks each PR before accepting it
  • The PR is open and its exact SHA still matches
  • The required CI passed for that exact code
  • The PR can be merged into its current base
  • The deployment plan and related PR links are valid

If every check passes, Release Bus saves the PR as waiting for staging. If a check fails, the PR is not added.

What is saved
  • Repository and PR number
  • Exact SHA
  • Deployment plan
  • Links to required candidates

Related candidates are linked by candidate ID. These saved links become the source of truth for deployment order.

Release Bus prepares the next staging round

Release Bus looks at the PRs waiting for staging.

It chooses the PRs that can move forward together. If one PR needs another PR first, it puts them in the correct order. Blocked PRs and the PRs that depend on them wait for a later round.

The chosen PRs become one exact staging round.

GitHub Actions combine the selected PRs

GitHub Actions handles the frontend and backend separately. For each repository, it starts from the current base version and adds the selected PRs in the order chosen by Release Bus.

If the PRs fit together, the result is one combined version that is ready to build and deploy.

If a PR causes a conflict, this staging round stops. That PR is marked as needing an update. PRs that depend on it wait. Independent PRs can be tried again in a later round.

The selected code is built and deployed to staging

GitHub Actions creates fresh builds for the code being released. Release Bus reserves the shared staging environment so only this release can change it.

Backend services are deployed in the required order. A frontend change waits for any backend change it needs. When everything succeeds, Release Bus saves the exact versions running in staging as STAGING_DEPLOYED.

If a code build fails, staging stays unchanged. PRs from the failed repository group are marked as failed. Dependent PRs wait, while independent PRs can return to the queue.

If a deployment fails, Release Bus retries only that deployment. If it keeps failing, Release Bus restores the last working frontend-and-backend combination.

Release Bus records the failed job and affected PRs. It identifies one PR as the cause only when the logs prove it.

The exact staging version is tested as one system

The E2E tests use the running staging system. They test important flows across the whole application, not just one small piece of code.

Release Bus keeps staging reserved during these tests. This makes sure nobody changes the tested version while the tests are running.

If all tests pass, Release Bus confirms that:

  • The expected frontend is running
  • The expected backend is running
  • The test results belong to those exact versions

The release is then marked STAGING_VALIDATED.

If a test fails, the release is not validated. Release Bus records the failed test and restores the last working frontend-and-backend combination. The logs may show the exact PR responsible, but an E2E failure can also come from several changes working badly together.

The agent chooses the safe production route

The agent reads the current production lane status. It uses live information because the status can change.

  • Production is ON → use Release Bus with exact code versions that passed staging
  • Production is OFF → use the manual process only when fallback is allowed, production is idle, and the owner approves
  • The status is missing or unsafe → stop without changing production

The result is one allowed route: Release Bus, safe manual fallback, or stop. Staging has its own separate lane status.

Only chosen, staging-validated PRs enter production

The agent sends Release Bus an exact list of candidates. Each candidate is one PR at one exact SHA that passed staging.

Release Bus checks that every selected SHA is unchanged and that the list includes all required PRs. If a frontend PR needs a backend PR, both are selected unless that exact backend version is already in production.

Unselected candidates keep their staging validation and stay out of production. The selected set is saved as one production request. Its source is the current main versions plus only those exact PR versions.

The selected PRs are combined with the current production code

Release Bus starts from the current frontend and backend main branches. It adds only the selected exact PR versions.

Frontend PRs are combined in a temporary frontend production branch. Backend PRs are combined in a separate temporary backend production branch. These branches hold the exact code being prepared for production.

Release Bus checks that every selected SHA is unchanged, its staging proof still matches, and all required PRs are included. Only PRs that combine cleanly are included in this exact production version.

If main changes while the temporary branches are being prepared, Release Bus prepares them again from the new main.

The exact production code is built from scratch

GitHub Actions builds the exact commits on the temporary production branches. Staging build files are not reused.

The frontend gets a fresh production build. The backend builds the selected services and packages the exact code they need.

If either build fails, the production attempt stops. main and the running production system stay unchanged.

Release Bus gets sole access to production

Release Bus reserves the production environment for this release. This prevents two releases from changing production at the same time.

It checks that production is idle and that the frontend and backend main branches still match the versions used to prepare the release.

If production is busy or a main branch has changed, Release Bus waits or prepares a new exact production version.

The prepared commits become the official source

Release Bus moves each affected main branch to the exact commit that was combined and built on its temporary production branch.

main points directly to the already-prepared commit. This keeps the official source exactly the same as the version that passed preparation.

If frontend and backend are both included, both main branches must reach their recorded commits. A partial update pauses production for exact recovery.

The prepared code is deployed to production

GitHub Actions deploys the fresh production builds. Backend services are deployed in the required order. A frontend change waits for any backend change it needs.

Release Bus retries a failed deployment without repeating work that already succeeded.

If deployment still fails, main stays on the new commits and the running system may be only partly updated. Release Bus pauses production until the exact running state is repaired or an explicit rollback is completed.

The running production system is checked

Read-only E2E tests check important user flows against the exact frontend and backend versions running in production.

Release Bus confirms that the test results belong to those exact deployed versions. A successful release is marked PRODUCTION_DEPLOYED.

If the tests fail, Release Bus pauses production. The recorded main commits and running versions must be checked, repaired, or explicitly rolled back before production releases resume.

Issues / gaps
There is no automatic tool that guarantees every affected service is found. The agent follows the skill rules and uses judgment.
The write-prs skill does not require exact related PR numbers or cross-PR dependency links in this step.
The write-prs skill asks for a service list and order. The deploy-6529 skill asks for a Release Bus plan. It does not say exactly how the first becomes the second.
