# Deploy job separation (design note)

Status: proposal. The current `Deploy a service` workflow
(`.github/workflows/deploy.yml`, generated by
`scripts/generate-deploy-config.mjs`) installs dependencies, builds, and deploys
in one job that holds `id-token: write` and the environment's secrets for its
whole lifetime. This note describes how to split that job so dependency
installation and builds run without deployment credentials.

## Target shape

```text
validate (no secrets, no id-token)
   └─ build (contents: read; no environment, no secrets, no id-token)
         └─ deploy (environment: staging|production; id-token: write)
```

### `validate` job

- Runs the existing dispatch-input, branch, `expected_source_sha`, and
  `AWS_DEPLOY_ROLE_ARN` checks. Outputs the validated service, environment, and
  account ID.

### `build` job

- `permissions: { contents: read }`, no `environment:`, so environment secrets
  and variables are not available. No `id-token: write`.
- Checks out `github.sha` with `persist-credentials: false` and verifies it.
- Installs with `./bin/6529 ci --ignore-scripts` where the service builds
  without lifecycle scripts. Keep an explicit allowlist (in
  `src/config/deploy-services.json`) for services that still need install
  scripts, and review that list when dependencies change.
- Runs the existing service build to produce `dist/index.zip` (and
  `src/api-serverless/dist/index.zip` for `api`).
- Writes a `SHA256SUMS` manifest for the packaged files and uploads the package
  and manifest with `actions/upload-artifact` (short retention). Publishes the
  package digest as a job output.

### `deploy` job

- `needs: [validate, build]`, `environment:` as today, `id-token: write`,
  `contents: read`, `actions: read`.
- Checks out the same `github.sha` for Serverless definitions and deploy
  scripts only. Installs only the pinned deploy tooling (the Serverless
  framework; the AWS CLI is on the runner image) from the lockfile with install
  scripts disabled; it does not rebuild application code.
- Downloads the artifact, verifies `SHA256SUMS` and that the digest equals the
  `build` job output, then places the package where the existing
  `package.artifact: dist/index.zip` settings expect it.
- Only then assumes the role through OIDC and runs the existing deploy,
  immutable-code (`CodeSha256`), stack, invocation, and health verification
  steps unchanged.

### Points to resolve before implementing

- Serverless resolves `${env:...}` and `${file(...)}` variables at deploy time.
  Keep `sls deploy` in the deploy job (with the prebuilt artifact) rather than
  running `sls package` in the build job, so environment values never enter the
  build job.
- Some workspace packages (for example image tooling) may need install scripts
  or native binaries for the target architecture. Confirm per service that the
  packaged zip is self-contained before enabling `--ignore-scripts`.
- The generator tests (`scripts/deploy-oidc.test.ts`,
  `scripts/deploy-source-guard.test.ts`) assume a single
  `build-and-deploy` job and must be updated with the generator.

## Role trust policy: bind to the workflow file

Today `ops/iam/backend-production/trust-policy.json` matches `aud` and
`sub = repo:6529-Collections/6529seize-backend:environment:production`. Any
workflow in the repository that runs in the `production` environment can
therefore assume the role. Bind the role to the deploy workflow as well:

```json
"StringEquals": {
  "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
  "token.actions.githubusercontent.com:sub": "repo:6529-Collections/6529seize-backend:environment:production",
  "token.actions.githubusercontent.com:job_workflow_ref": "6529-Collections/6529seize-backend/.github/workflows/deploy.yml@refs/heads/main"
}
```

Staging uses `environment:staging` and `@refs/heads/1a-staging`. The staging
trust policy is not yet committed under `ops/iam/backend-staging/`; add it
alongside this change so both roles are reviewed together.

Rollout:

1. Confirm that IAM evaluates `job_workflow_ref` as a condition key for the
   GitHub OIDC provider in this account. If it does not, customize the
   repository's OIDC subject template to include `job_workflow_ref`
   (`include_claim_keys: ["repo", "context", "job_workflow_ref"]`) and match the
   resulting `sub` value instead; update every role trusting this repository
   before switching the template.
2. Apply the condition to the staging role first and run one staging deploy.
3. Apply to production and run one low-risk production deploy.
4. Commit the applied trust policies under `ops/iam/` and update the README.
